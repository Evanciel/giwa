# 결정 기록 (ADR)

> 형식: 배경 · 결정 · 대안 · 결과. 스펙(`docs/SPEC.md`)과 다른 결정은 반드시 여기에 남긴다.
> 0001~0015는 2026-11-02 Phase 1 계획(`docs/PHASE1_PLAN.md`) 승인과 함께 확정됐다.

---

## ADR-0001 글 발행은 changeset이 아니다

- **배경:** `CLAUDE.md` 원칙 4와 SPEC §6 첫 줄은 "구조·디자인·발행 변경"을 changeset으로 묶는다. 그러나 SPEC §1.2, §5.3, §6 끝, §11은 발행을 `publish` 스코프와 감사 로그로만 다룬다.
- **결정:** SPEC §11을 따른다. changeset 대상은 구조, 디자인, 모듈, 설정이다. 글 발행·숨김·삭제는 `publish` 스코프와 감사 로그로 통제한다. Phase 1에는 changeset이 없으므로 구조 변경은 바로 적용하고, 변경 전 값을 `audit_log.diff`에 남겨 Phase 3 역연산에 재사용한다.
- **대안:** 발행도 changeset으로 묶는다. 운영 시나리오 "공지 써줘 → 확인 → 발행"이 미리보기·승인 2단계가 되어 무거워진다.
- **결과:** 원칙 4의 문구를 Phase 3 착수 시 "구조·디자인·모듈·설정"으로 고친다.

## ADR-0002 로컬 CLI의 Actor는 `local`

- **배경:** SPEC §3.1의 CLI는 DB를 직접 연다. 셸을 쓰는 에이전트는 §5.3의 스코프와 "적용은 사람만" 규칙을 우회할 수 있다.
- **결정:** CLI는 `ActorKind::Local`(운영자 권한)로 동작한다. 환경변수 `MARU_TOKEN`이 있으면 그 토큰의 Actor와 스코프를 강제한다. `posts.actor_type`에 `local` 값을 추가한다.
- **대안:** CLI도 항상 토큰을 요구한다. 같은 OS 계정에서는 DB 파일을 직접 고칠 수 있어 보안 경계가 되지 못하고 사용성만 해친다.
- **결과:** 같은 OS 계정 안에서는 안전장치일 뿐 보안 경계가 아니다. Phase 3에서 에이전트 쓰기를 MCP로 유도한다.

## ADR-0003 Phase 1 범위: 최소 REST 포함, 태그·검색·위젯 제외

- **배경:** SPEC §15 Phase 1에는 REST가 없지만 `CLAUDE.md`와 착수 프롬프트에는 있다. `init`은 초기 토큰을 발급하는데 `maru token`은 Phase 1 CLI 목록에 없다. `blog` 프리셋의 태그·검색·최신글 위젯은 Phase 1에 없고 태그는 데이터 모델에도 없다.
- **결정:** Phase 1에 최소 REST(`/api/v1`, bearer 토큰)와 `maru token`을 넣는다. 태그·검색·위젯은 Phase 2로 미루고, 홈 최신글은 템플릿에 고정한다.
- **결과:** Phase 1 `blog` 프리셋은 SPEC §8.6 표보다 작다.

## ADR-0004 owner 초기 자격증명은 1회용 로그인 링크

- **배경:** SPEC §10 `init`에는 owner 입력 인자가 없다. 생성한 비밀번호를 JSON으로 내면 에이전트 대화 기록에 남고, 분실 시 복구 명령도 없다.
- **결정:** `init`은 비밀번호를 만들지 않는다. 10분짜리 1회용 로그인 링크를 내고, `maru login-link`로 재발급한다. 초기 토큰은 `read`, `draft` 스코프로 1회만 표시한다.
- **결과:** 링크는 GET에서 확인 화면만 보이고 POST에서 소비한다(ADR-0009). `sessions`, `login_tickets` 테이블을 추가한다.

## ADR-0005 이름 `maru`, 라이선스 `MIT OR Apache-2.0`

- **배경:** SPEC §16 열린 질문. crates.io에서 `maru`(0.0.1, 2023)는 등록돼 있고 `maru-core`, `maru-cli`는 비어 있다(2026-11-02 조회).
- **결정:** 크레이트 접두어와 바이너리 이름은 `maru`. 라이선스는 `MIT OR Apache-2.0`. 공개 전에 한 번 더 확정한다.
- **대안:** AGPL. 호스팅 SaaS가 범위 밖이라 무임승차 위험이 낮고, 에이전시 납품이 쉬워야 해서 허용형을 택했다. 공개 후 AGPL로 바꿔도 이미 낸 릴리스에는 소급되지 않는다.

## ADR-0006 세로 슬라이스 우선

- **배경:** 층별로 서비스를 쌓고 마지막에 연결하면, 격리된 CRUD만 통과하고 실제 통합이 깨진 상태를 늦게 발견한다.
- **결정:** M1(U3~U6)에서 `init → REST 초안 → CLI 발행 → 공개 페이지 → DB 감사 로그` 경로를 먼저 완성한다(E2E-1). 이후 단위는 이 경로를 넓힌다.

## ADR-0007 쓰기 경계 `WriteTx`

- **배경:** `CLAUDE.md`는 "모든 쓰기는 audit_log에 기록"을 요구한다. 테스트만으로는 누락을 막지 못한다.
- **결정:** 저장소의 쓰기 메서드는 `WriteTx`로만 호출할 수 있다. `WriteTx`는 `BEGIN IMMEDIATE`로 시작하고, 감사 기록이 0건이면 `commit()`이 실패한다. 권한 검사·쓰기·감사가 한 트랜잭션이다.
- **대안:** 서비스마다 감사 호출을 두고 테스트로 확인. 누락이 구조적으로 가능하다.
- **결과:** U4 중단 기준(`dyn Store` 트랜잭션 소유, `query!` 매크로 궁합, 동시 쓰기)이 풀리지 않으면 `Ctx<S: Store>` 제네릭 구조로 바꾸고 이 ADR을 갱신한다.

## ADR-0008 감사 범위

- **결정:** 감사 대상은 도메인 쓰기, 로그인 성공·실패, 비밀번호 변경, 토큰 발급·폐기. 제외는 `last_used_at` 갱신, 세션 만료 정리처럼 시스템이 자동으로 남기는 기록. `diff`에서 `password_hash`, `token_hash`, 원문 토큰은 제거한다.

## ADR-0009 토큰 해시와 로그인 티켓

- **배경:** `CLAUDE.md` 표는 인증에 argon2만 적었다.
- **결정:** 사람이 고른 비밀번호는 argon2id. 서버가 만든 긴 무작위 값(API 토큰, 세션, 로그인 링크)은 SHA-256으로 해시한다. 엔트로피가 충분해 느린 해시가 필요 없고, 요청마다 검증하므로 빨라야 한다. 로그인 링크는 GET 확인 화면, POST 소비, 10분, 1회.
- **결과:** `sha2` 의존을 추가한다. `CLAUDE.md` 기술 스택 표의 인증 행을 갱신한다.

## ADR-0010 Phase별 스키마

- **배경:** SPEC §4는 전체 Phase의 컬럼을 한 번에 정의한다.
- **결정:** 읽는 코드가 생기는 Phase의 마이그레이션에서 컬럼을 추가한다. Phase 1에서 빼는 컬럼은 `PHASE1_PLAN.md` §5에 있다. `media` 테이블은 SPEC §15 목록에 있어 만들지만 Phase 1에는 읽는 코드가 없다.
- **대안:** 미리 다 만든다. 읽는 코드 없는 선언은 동작으로 착각하기 쉽다. SQLite는 `ADD COLUMN`이 싸다.

## ADR-0011 공개 URL 체계

- **결정:** `/`, `/b/{board}`, `/b/{board}/{post}`, `/p/{page}`, `/sitemap.xml`, `/rss.xml`, `/robots.txt`, `/admin`, `/api/v1`. 한글 슬러그 허용, NFC 정규화. 유일성은 `(board_id, slug)`. 절대 URL은 `config.toml`의 `site_url`로만 만들고 `Host` 헤더를 쓰지 않는다. 슬러그 변경 시 옛 주소는 Phase 1에서 404.

## ADR-0012 게시판 삭제는 글이 있으면 거부

- **결정:** 글이 하나라도 있는 게시판의 삭제는 `CONFLICT`(종료 코드 4)로 거부하고 `next`에 글 이동·숨김 명령을 준다.

## ADR-0013 Mono 폰트

- **배경:** SPEC §8.2 예시 토큰은 `mono: D2Coding`.
- **결정:** Phase 1은 시스템 고정폭 글꼴 스택을 쓴다. D2Coding 내장은 라이선스·용량 확인 후 추후 결정한다.

## ADR-0014 개발 포트 3139

- **배경:** 사용자 환경에서 8080은 흔히 점유된다.
- **결정:** 제품 기본값은 SPEC대로 `127.0.0.1:8080`. 개발·수동 확인은 3139(`PORT-REGISTRY.md` 등록). 자동 E2E는 0번 포트로 빈 포트를 받는다.

## ADR-0015 빌드 산출물 위치

- **배경:** 저장소 경로에 한글이 있다. 처음에는 전역 지침대로 F:에 두었다. 그런데 F:(USB 연결 SSD)는 작은 파일 300개를 쓰는 데 24초가 걸려(E: 0.8초, H: 1.1초, 2026-11-02 실측) 크레이트 압축 해제와 빌드가 수십 분씩 걸렸다.
- **결정:** Rust 툴체인(`RUSTUP_HOME`), 크레이트 캐시(`CARGO_HOME`), 빌드 산출물(`target`)을 모두 `H:\maru-build` 아래에 둔다(사용자 지시, 여유 858GB). `target`은 저장소에 커밋하지 않는 `.cargo/config.toml`로 지정한다.
- **대안:** F: 유지(빌드가 매번 수십 분 걸림), E:(저장소 드라이브, 여유 42GB).
- **결과:** 이 프로젝트에 한해 전역 지침의 「중간 산출물은 F:」 대신 H:를 쓴다. 이전 설치본 `F:\rust`는 더 이상 쓰지 않는다.

## ADR-0016 늘어날 열거 값은 core에서 검증하고 DB CHECK를 걸지 않는다

- **배경:** 목표가 「콘텐츠 중심 사이트라면 무엇이든」으로 넓어지면서 `boards.kind`, `pages.layout`, `menus.location`, `audit_log.target_type`·`action`의 값이 Phase마다 늘어난다. SQLite는 ALTER TABLE로 CHECK 제약을 바꿀 수 없고, 바꾸려면 공식 문서의 12단계 테이블 재작성 절차가 필요하다.
- **결정:** 위 열거 값은 `TEXT NOT NULL`로만 두고 값 검증은 core 타입에서 한다. 상태 기계 값(`posts.status`, `posts.kind`, `actor_type`)은 값이 바뀌면 전이 규칙도 함께 바뀌므로 CHECK를 유지한다.
- **대안:** 모든 열거 값에 CHECK. DB 수준 무결성은 강하지만 값을 추가할 때마다 테이블 재작성 마이그레이션이 필요하다. 쓰기는 `WriteTx`(ADR-0007)를 통해 core만 하므로 core 검증으로 충분하다.
- **결과:** U3·U9 마이그레이션에 반영한다. DB를 직접 고치는 경우의 잘못된 값은 읽을 때 `INTERNAL`이 아니라 「알 수 없는 kind」 경고로 처리한다.

## ADR-0017 공개 URL은 단일 URL 빌더로만 만든다

- **배경:** ADR-0011이 공개 URL을 정했지만, 이후 컬렉션 퍼머링크·홈 교체·페이지 계층(ADR-0021)으로 URL 모양이 바뀐다. Phase 1부터 사용자 테마 복사가 가능하다(U10).
- **결정:** `url_for(Target)` 하나가 모든 공개 경로를 만든다. 템플릿은 `post.url`, `url_for()`만 쓰고 경로 문자열을 조합하지 않는다. 사이트맵, RSS, canonical, `next` 힌트, 관리 화면, CLI 출력이 같은 함수를 쓴다. 절대 URL은 `site_url` + 이 경로(ADR-0011 유지).
- **대안:** 템플릿에서 문자열 조합. 퍼머링크 변경 시 내장·사용자 테마를 모두 고쳐야 한다.
- **결과:** 내장 테마 검사 스크립트(PHASE1_PLAN §7)에 「템플릿 안 `/b/`, `/p/` 문자열 리터럴 금지」를 추가한다.

## ADR-0018 공통 필드 타입 체계

- **배경:** SPEC §2·§4의 `field_schema`는 「JSON Schema」로만 정의돼 렌더·검증·조회 계약이 없다. 블록(§8.5), 위젯(§7.2 `config_schema`), 모듈 설정(§7.1 `settings_schema`), 폼도 같은 문제를 가진다.
- **결정:** Maru 필드 타입(`text`, `textarea`, `markdown`, `number`, `boolean`, `date`, `datetime`, `select`, `multiselect`, `url`, `email`, `phone`, `media`, `ref`, `group`, `list`)을 정의하고 컬렉션·블록·위젯·폼·모듈 설정이 공유한다. JSON Schema는 필드 정의에서 생성해 MCP·REST 입력 스키마로 쓴다. 검증은 core에서 한다. `markdown` 타입만 정화된 HTML로 렌더한다.
- **대안:** 임의 JSON Schema 허용(렌더 계약 불가), 용도별 별도 스키마(중복).
- **결과:** Phase 2 산출물. 모듈 매니페스트(§7.1)의 `settings_schema`도 이 형식으로 바꾼다.

## ADR-0019 게시판을 정의 가능한 컬렉션으로 일반화한다

- **배경:** `boards.kind` 6개로는 포트폴리오, 행사, 채용, 강의, 매거진을 표현할 수 없다(제안서 §2).
- **결정:** `boards`·`posts` 단일 테이블 구조를 유지한 채, 컬렉션 정의(필드, 기능 플래그, 정렬 기준, 뷰, 퍼머링크)를 changeset op `collection.define`으로 만든다. `kind`는 닫힌 타입이 아니라 출발점 묶음이며 `custom`을 추가한다. meta 필드 필터·정렬은 `index: true` 필드만, SQLite JSON 식 부분 인덱스로 지원한다. 런타임 DDL은 필드 키 정규식 검증 후 `AssertSqlSafe`로만 실행한다. 뷰 템플릿은 `collections/{slug}` → `kinds/{kind}` → 기본 순서로 찾는다.
- **대안:** kind 추가(유형마다 코어 수정), 컬렉션별 테이블(그누보드식 회귀, SPEC §2에서 버림).
- **결과:** Phase 2(b). `field_schema`, `meta`, `view_template` 컬럼은 이때 추가한다(ADR-0010).

## ADR-0020 블록 타입과 위젯 타입을 하나의 렌더 계약으로 통합한다

- **배경:** SPEC은 위젯(§7.2)과 섹션 블록(§8.5)을 따로 두지만 둘 다 「스키마 + 렌더」다. 블록 데이터 모델과 렌더 계약이 없고, §8.5 카탈로그와 §8.6 프리셋 설명이 어긋난다(연혁, 조직도, 가격표).
- **결정:** `BlockType` 트레이트 하나(`id`, `name`, 필드 정의, `render`). 블록 인스턴스는 페이지 `blocks` 배열에, 위젯 인스턴스는 `widget_instances`에 저장하고 같은 타입을 가리킨다. 인스턴스는 `{id, type, v, variant, spacing, tone, data}`. 템플릿은 검증된 data와 선언형 질의 결과만 받는다. 블록 정의는 `block.toml` + `block.html`, 버전 변경은 선언형 변환만. 렌더 실패는 해당 블록만 비운다.
- **대안:** 위젯·블록 별도 유지. 모듈이 같은 기능을 두 번 등록하고 에이전트가 둘을 구분해야 한다.
- **결과:** Phase 2(a). 모듈 트레이트의 `widgets()`는 `block_types()`로 바꾼다. §8.5 카탈로그를 보강한다.

## ADR-0021 홈 설정, 컬렉션 퍼머링크, 페이지 계층, 리다이렉트

- **배경:** ADR-0003은 홈을 템플릿에 고정했고 ADR-0011은 URL 모양과 「슬러그 변경 시 404」를 정했다. 회사 소개·랜딩·문서·이전에서 막힌다.
- **결정:** `site_settings.home`(latest | page | collection), 컬렉션 `permalink` 패턴(`{slug}`, `{yyyy}`, `{mm}`, `{dd}`, `{category}`), `pages.parent_id`·`sort_order`와 경로형 URL, `redirects` 테이블(슬러그 변경 시 자동 301, Phase 1 이력은 `audit_log.diff`에서 소급), 예약 경로 목록과 충돌 시 `CONFLICT`. 라우트 표는 프로세스 캐시 없이 읽는다(PHASE1_PLAN §4.4). 기본값은 ADR-0011 그대로.
- **대안:** Ghost식 사용자 정의 라우트 파일. 표현력은 크지만 위 네 가지로 대부분의 수요가 풀린다. Phase 3 이후 필요 시 추가한다.
- **결과:** Phase 2(b). 라우트 변경은 구조 변경이므로 Phase 3부터 changeset 미리보기를 탄다. 다국어 접두어는 설계하지 않되 막지 않는다.

## ADR-0022 테마 자유도 단계와 테마 파일 changeset

- **배경:** 토큰(§8.2)과 사용자 테마 복사(§3.3, U10) 사이의 경계가 없고, 테마 파일 변경이 changeset(§6) 밖이라 원칙 4의 롤백이 디자인에서 깨진다.
- **결정:** L0 토큰, L1 블록 선택지, L2 템플릿 덮어쓰기·사용자 블록, L3 사용자 CSS 하나, L4 사용자 JS(사람 명시 허용 시만). L0~L3 변경은 changeset op(`theme.write_file`·`delete_file`, `base_hash`, 이전 내용 저장)로만. 템플릿 로더는 `changeset 오버레이 → 사용자 테마 → 내장` 겹 구조. `theme.toml`에 `template_api` 번호와 `[[assets]]` 출처·라이선스 목록, 목록 밖 자산은 검증 실패. 관리 화면은 덮어쓸 수 없다. 사용자 CSS는 외부 `@import`·`url()` 거부.
- **대안:** 토큰만 허용(디자인 다양성 부족), 파일 편집을 changeset 밖에 둠(롤백 불가).
- **결과:** Phase 3. 사용자 테마 파일 원본은 디스크에 두고 해시로 changeset과 대조한다(제안서 Q3). L4 사용자 JS는 Phase 4 이후, owner가 명시로 허용할 때만 연다(Q5). 원칙 7은 자산 출처 목록, 승인 화면의 출처 표시, `AGENTS.md`의 「OO 사이트처럼」 처리 규칙으로 운영한다. 기술적으로 완전한 차단은 아니라는 점을 문서에 적는다.

## ADR-0023 프리셋을 조합 가능한 레시피로 재정의한다

- **배경:** 프리셋(§8.6)은 유형별 고정 세트라 조합(「카페 + 블로그 + 문의」)을 표현하지 못한다.
- **결정:** 레시피 = 매개변수화된 changeset op 묶음(`ensure` 의미로 멱등). 레시피 적용은 changeset 하나를 만든다. 프리셋 = 레시피 목록 + 테마 + 토큰. CLI `maru recipe`, MCP `list_recipes`·`apply_recipe`. 제안서 §2의 유형 매트릭스를 레시피 조합으로 정의해 Phase 4 회귀 시험으로 쓴다.
- **대안:** 프리셋 추가(조합 폭발), 에이전트의 저수준 op 직접 조립(품질 편차).
- **결과:** 형식은 Phase 3, 기존 5개 프리셋 재정의와 Phase 4 완료 기준 변경은 Phase 4.

## ADR-0024 기존 사이트 이전의 범위와 소유 확인

- **배경:** 실사용자는 기존 사이트에서 옮겨 온다. 원칙 7은 디자인 복제를 금지하고, 원칙 6은 외부 입력을 데이터로만 다룬다.
- **결정:** 이전 대상은 사용자 소유의 콘텐츠·미디어·URL·정보 구조·브랜드 토큰이다. 이전 도구는 디자인 코드(HTML·CSS·JS)를 자동으로 옮기지 않고 Maru 블록·토큰으로 재구성한다. 상용 테마 자산과 제3자 사이트는 대상이 아니다. 내보내기 파일(WXR, 그누보드 덤프, Markdown)은 사용자가 제공하고, 원본 사이트를 직접 읽는 기능은 소유 확인(`.well-known` 파일 또는 DNS TXT)한 도메인에만 허용한다. 가져온 본문은 정화하고 MCP에서 `untrusted`로 분리한다. 구조는 changeset, 글은 `draft` 일괄 생성(원 발행일 보존), 옛 URL은 리다이렉트.
- **대안:** 임의 URL 크롤링 가져오기. 에이전트가 제3자 사이트를 복제하는 통로가 된다.
- **결과:** 코어 일괄 생성 API는 Phase 4, 소스별 가져오기는 공식 모듈(`import_gnuboard`, `import_wordpress`)로 Phase 4 이후. 사용자가 직접 만든 자기 사이트의 테마 코드를 사용자 테마로 손수 옮기는 것은 허용한다(제안서 Q4). 이전 도구가 디자인 코드를 자동 이식하는 것은 어느 경우에도 하지 않는다.

## ADR-0025 폼 제출과 첨부 파일은 공식 모듈로 둔다

- **배경:** 연락처 폼 블록(§8.5)과 「문의」(§5.3)는 있지만 제출 저장소가 없고, 자료실(§8.6 `org`)은 첨부 파일이 필요하다.
- **결정:** `forms` 공식 모듈(폼 정의는 ADR-0018 필드 타입, `form_submissions`, 스팸 방지, 수집 동의·보관 기간·자동 삭제, MCP 응답 `untrusted` 분리, `form.submitted` 이벤트). 첨부는 문서 파일 허용 목록, `Content-Disposition: attachment`·`nosniff`, 실행 파일·HTML·SVG 거부, `media` 필드 타입으로 연결. SMS 알림은 범위 밖 유지, 메일 발송은 별도 결정.
- **대안:** 외부 폼 서비스. 셀프호스팅·단일 바이너리 원칙과 어긋나고 데이터가 밖으로 나간다.
- **결과:** Phase 4. 개인정보 관련 법적 요건은 구현 시점에 공식 자료로 확인한다.

## ADR-0026 목표 재정의: 콘텐츠 중심 사이트라면 무엇이든

- **배경:** 사용자가 목표를 「특정 유형뿐 아니라 어떤 사이트나 블로그든 이 코어로 만들 수 있게」로 넓혔다. SPEC §0은 홈페이지·게시판·커뮤니티·블로그를 열거한다.

- **대안:** 기존 4개 유형 유지. 막히는 유형(문서, 행사, 강의)이 구조적으로 남는다.
- **결과:** SPEC §0 문구는 사용자가 SPEC을 고칠 때 이 ADR을 따른다. 그 전까지 이 ADR이 SPEC §0보다 우선한다. `AGENTS.md`(Phase 3)에 같은 정의를 쓴다.

- **배경:** 컬렉션·블록·라우팅(ADR-0018~0021)이 들어가면 Phase 2(원래 2~3주)가 약 5~6주가 된다. SPEC은 Phase마다 실제 운영 검증을 요구한다.

- **결과:** Phase 1 범위는 늘지 않는다. Phase 1에는 ADR-0016, ADR-0017과 저비용 준비 3건(겹 구조 템플릿 로더, `template_api = 1`, 프리셋 `[[ops]]` 형식)만 반영한다(`PHASE1_PLAN.md` §2).

## ADR-0028 결제·본인확인·쇼핑몰·시각 편집기는 Phase 5 이후 공식 모듈, 다국어는 Phase 2b에서 코어 축 설계

- **결정:**
  - 결제, 본인확인, 쇼핑몰, 시각 편집기는 **Phase 5 이후 공식 모듈**로 만든다. 코어는 Phase 2a 모듈 시스템(SPEC §7)이 이들을 수용할 수 있는지 설계 단계에서 점검한다(모듈 마이그레이션, 라우트, 이벤트, 권한, 관리 화면 확장 지점).

  - SMS는 범위 밖으로 유지한다.
- **대안:** SPEC §0을 유지한다. 그누보드7 대비 기능 폭에서 계속 밀린다.
- **결과:** 결제·본인확인은 PG사 가맹 계약, 본인확인기관 계약처럼 코드 밖 조건이 있다. 모듈 착수 시 공식 문서와 법적 요건(전자상거래법 등)을 확인하고, 사용자 사업자 정보가 필요한 단계에서 멈추고 묻는다.

## ADR-0029 그누보드7 분석에서 온 Phase 1 보강

- **배경:** 그누보드7 분석 §10.3이 Phase 1 스키마·권한에 작은 보강을 제안했다.
- **결정:**
  1. 권한 범위: 본인 글 수정·삭제는 `post.write`, 남의 글 수정·삭제·숨김은 `post.moderate`로 정한다. 권한 매트릭스 테스트에 「본인/타인」 축을 더한다.
  2. `posts.author_id`는 nullable로 둔다. `local`·에이전트 Actor와 이후 비회원 글을 위해서다. 작성 주체는 `actor_type`과 `audit_log`로 추적한다.
  3. 삭제는 되돌릴 수 있어야 한다. `posts.status`에 `deleted`를 추가하고, 공개 조회 함수 하나(`PHASE1_PLAN.md` §4.6)에서 제외한다. 영구 삭제는 Phase 1에 두지 않는다.
  4. `guest`를 실제 역할로 시드하고, 비로그인 `Anonymous` Actor는 한곳에서 `guest`로 연결한다.
  5. API 토큰과 세션 값을 브라우저 `localStorage`에 두지 않는다. 관리 화면은 HttpOnly 세션 쿠키 + CSRF 토큰만 쓴다.
  6. `init`, `serve`, `doctor`를 root/Administrator로 실행하면 경고하고 계속 진행한다(사용자 결정: 거부하지 않고 경고만). `doctor`는 이 항목을 점검 결과에 넣는다.
- **대안:** 그대로 둔다. 영구 삭제만 있으면 에이전트 실수를 되돌릴 수 없다.
- **결과:** U3 스키마, U4 권한, U8 글 전이, U12 세션, U14 doctor에 반영한다. 프리셋 재적용 시 운영자가 고친 값을 보존하는 추적(그누보드7의 사용자 수정 기록)은 Phase 3 레시피(ADR-0023)에서 정한다.

## ADR-0030 쓰기 경계는 `Arc<dyn Store>` + core 의 `Tx` 래퍼로 확정 (U4 스파이크 결과)

- **배경:** `PHASE1_PLAN.md` U4 중단 기준 3가지를 실측했다.
- **결정:**
  - `Store`, `WriteTx`는 `async_trait` 기반 트레이트 객체다. sqlx 의 `Pool::begin_with("BEGIN IMMEDIATE")`가 `Transaction<'static, Sqlite>`를 돌려주므로 `Box<dyn WriteTx>`가 트랜잭션을 그대로 소유한다(기준 1 통과).
  - 저장소 구현은 `query!`·`query_as!`로 쓰고, 읽기·쓰기에서 같은 쿼리는 `impl SqliteExecutor` 를 받는 함수로 공유한다. 행 타입 → 도메인 타입 변환에서 알 수 없는 열거 값은 `INTERNAL` 이다(기준 2 통과).
  - 감사 강제는 core 의 `Tx` 래퍼가 한다. `Tx::audit`만 감사 횟수를 세고, `Tx::commit`은 0건이면 거부한다. 저장소 구현이 바뀌어도 이 규칙은 core 에 남는다.
  - 공개 범위 SQL 은 `list_published`·`count_published` 두 쿼리에만 있다. 게시판 `policy.read` 역할 이름을 `roles`와 조인해 서열을 비교하고, 모르는 역할은 결과에서 빠진다(닫힌 쪽 실패).
- **측정:** 연결 풀 둘(서버와 CLI 를 흉내)이 동시에 글 40편씩 쓰기 → 80편, 감사 80건, `SQLITE_BUSY` 0건(기준 3 통과, `busy_timeout` 10초). 감사 트리거를 실패시키면 글·리비전 0건으로 롤백. 감사 없는 커밋은 `INTERNAL`로 거부.
- **대안:** `Ctx<S: Store>` 제네릭. 필요 없어졌다.
- **결과:** 에이전트 Actor 의 「본인 글」은 `author_id IS NULL AND actor_type = 'agent'` 로 판단한다. 토큰마다 구분하지 않으므로, 토큰별 소유가 필요해지면 `posts`에 작성 토큰 컬럼을 추가하는 마이그레이션으로 바꾼다.

## ADR-0031 SEO 출력은 표준 규격 기준, 네이버 요건은 공개 후 도구로 검증

- **배경:** PHASE1_PLAN §M3는 U11 착수 전에 네이버 서치어드바이저 공식 문서를 확인하라고 한다. 2026-11-02 시점에 `searchadvisor.naver.com` 은 작업 환경(WebFetch, 내장 브라우저)에서 접근이 막혀 있었고, 검색 결과는 개인 블로그 글뿐이었다.
- **결정:** 사이트맵은 sitemaps.org 0.9(파일당 50,000 URL), 피드는 RSS 2.0(`atom:link rel=self`, `guid isPermaLink`, RFC 2822 `pubDate`, 본문 전체를 정화된 HTML CDATA로), 메타는 Open Graph(`og:type`, `og:title`, `og:description`, `og:url`, `og:site_name`, `og:locale`, `article:*_time`)와 canonical로 맞춘다. 소유 확인 meta(`naver-site-verification`, `google-site-verification`)는 사이트 설정으로 넣는다. robots.txt는 `/api/`만 막고 사이트맵 절대 URL을 적는다.
- **대안:** 블로그 글의 요건 요약을 그대로 따르기. 출처가 공식이 아니라 채택하지 않는다.
- **결과:** `maru expose` 로 공개한 뒤 서치어드바이저의 「사이트 간단 체크」와 RSS·사이트맵 제출 결과로 실제 수집 여부를 확인하고, 어긋나는 항목은 이 ADR을 갱신한다. 그 전까지 이 항목은 완료 검증표에서 「못 쟀다」로 둔다.

## ADR-0032 미디어 저장 형식과 업로드 경로

- **배경:** SPEC §2·§13은 「썸네일, webp 변환」과 「MIME 스니핑 + 확장자 화이트리스트, 이미지 재인코딩, 크기 제한」을 요구한다. 순수 Rust `image` 0.25(`image-webp` 0.2)의 WebP 인코더는 무손실만 지원한다. 사진을 무손실 WebP로 바꾸면 JPEG보다 몇 배 커진다. 손실 WebP는 C 라이브러리(libwebp)가 필요해 단일 바이너리·교차 빌드를 복잡하게 만든다.
- **결정:**
  - 받는 형식은 jpg·png·gif·webp, 10MB, 한 변 8192px, 디코딩 메모리 300MB까지. 확장자와 내용 스니핑이 둘 다 그림이어야 한다. SVG는 받지 않는다(스크립트를 품을 수 있다).
  - 원본은 항상 다시 인코딩한다. 그래서 EXIF(촬영 위치)와 그림 뒤에 덧붙인 데이터가 사라진다. EXIF 방향은 인코딩 전에 적용한다.
  - 저장 형식은 JPEG(품질 85)와 PNG 둘뿐이다. JPEG는 JPEG로, 투명도 없는 WebP는 JPEG로, PNG·투명 WebP는 PNG로, GIF는 첫 장만 PNG로 저장한다(움직임은 사라진다).
  - 축소본은 폭 640·1280 두 가지이고, 원본이 그보다 넓을 때만 만든다. 같은 형식이다.
  - 경로는 `media/YYYY/MM/<ulid>[-<폭>].<확장자>`. 사용자가 준 파일 이름은 경로에 넣지 않는다. 보관소는 core 의 `Blobs` 트레이트, 구현은 storage 의 `FsBlobs`(임시 이름으로 쓰고 바꾸기).
  - 업로드 본문은 multipart 가 아니라 원본 바이트를 받는다(`POST /api/v1/media?filename=`, `POST /admin/media?filename=`). `curl --data-binary`, 브라우저 `fetch(file)`, CLI 가 같은 모양이고 새 의존성이 없다.
  - 디코딩·인코딩은 웹에서 `spawn_blocking` 으로, 동시에 2개까지 돌린다. core 는 tokio 에 의존하지 않는다.
  - `/media/*` 는 `Cache-Control: immutable`, `nosniff`, `CSP: default-src 'none'; sandbox`로 내보낸다.
- **대안:** libwebp 로 손실 WebP 변환. 용량은 가장 작지만 C 의존이 생긴다. 순수 Rust 손실 WebP 인코더가 나오면 저장 형식에 WebP를 더하고 이 ADR을 갱신한다.
- **결과:** SPEC의 「webp 변환」은 보류한다. 공개 화면의 `srcset`(축소본 활용)은 테마 작업에서 한다. MCP 툴(`upload_media`, `list_media`, `set_alt_text`)은 Phase 3 MCP 서버에서 같은 서비스를 노출한다.

## ADR-0033 글 에디터는 ProseMirror 위에 직접 만든 Maru 층, 저장 형식은 Markdown

- **배경:** 관리 화면의 글쓰기는 textarea 하나였다. 블로그를 쓰려면 서식 도구, 이미지 붙여 넣기·끌어 놓기, 미리보기가 필요하다. 후보는 TOAST UI Editor(MIT)를 그대로 쓰기, Tiptap, 직접 만들기였다. TOAST UI 는 2023년 이후 유지보수가 사실상 멈췄고, 번들이 크고(약 500KB+), 자체 Markdown 파서로 미리보기를 그려 서버 렌더러(pulldown-cmark + ammonia)와 결과가 어긋날 수 있다. 다만 그 구조(Markdown·WYSIWYG 두 모드가 같은 원문을 공유, 이미지 업로드 훅, 도구 막대 명령 레지스트리)는 검증된 설계라 구조만 분석했다.
- **결정:**
  - 편집 엔진은 ProseMirror(MIT), 그 위의 도구 막대·단축키·입력 규칙·업로드·자동 저장·CSS 는 직접 만든다(`editor/`, TypeScript). esbuild 로 IIFE 번들 하나(`editor.js`)를 만들어 커밋하고 rust-embed 로 바이너리에 넣는다. 실행 시 Node 가 필요 없다(원칙 5).
  - 원문은 언제나 textarea 의 Markdown 이다. 스크립트가 꺼져도 폼은 그대로 저장된다. 모드는 서식(ProseMirror), Markdown(textarea), 미리보기 셋이고, 미리보기는 `POST /admin/preview` 로 서버 렌더러가 그린다(공개 화면과 같은 HTML).
  - 손실 방지: 글을 열 때 parse → serialize 한 결과와 원문을 markdown-it 으로 각각 HTML 로 그려 비교한다. 다르거나 표·HTML·할 일 목록·각주가 있으면 서식 모드를 막고 Markdown 으로 연다. 이미 연 원문은 덮어쓰지 않는다.
  - 이미지는 서버에 원본 바이트로 올린다(ADR-0032, `POST /admin/media`, 세션 쿠키 + `X-CSRF-Token`). TOAST UI 기본값인 base64 본문 삽입은 쓰지 않는다. 클립보드 그림처럼 이름이 의미 없으면 대체 텍스트를 비워 두고 쓰라고 안내한다.
  - 자동 저장은 브라우저 localStorage 에 글별로(폼 주소 기준) 둔다. 비밀값이 아니라 쓰던 원고이고, 제출하면 지운다.
  - 관리 화면 CSP 는 `script-src 'self'`, `connect-src 'self'`, `style-src 'self'`(인라인 없음)로 연다.
  - 번들에 들어간 패키지의 라이선스 전문은 빌드 때 `editor.licenses.txt` 로 모은다(THIRD_PARTY.md).
- **대안:** TOAST UI 그대로 — 유지보수 정지, 렌더러 불일치. Tiptap — ProseMirror 위의 층이라 장점이 겹치고 Markdown 왕복은 별도 확장에 기대야 한다. contenteditable 직접 구현 — 한글 IME·선택 처리 비용이 너무 크다.
- **결과:** 번들 약 370KB(압축 전). tower-http 압축, 표 서식 편집, 붙여 넣은 HTML 의 외부 이미지 처리, 공개 화면 `srcset` 은 후속으로 둔다. 한글 IME 조합·실제 끌어 놓기·파일 선택은 자동 검증이 닿지 않으므로 바꿀 때마다 사람이 확인한다.

## ADR-0034 글 꾸밈은 Markdown 확장 문법(directive)으로, 값은 정해진 팔레트 안에서만

- **배경:** 네이버 블로그 수준의 글쓰기에는 강조 상자, 문단 정렬, 글자 색·형광펜·크기가 필요하다. 원문은 Markdown 이어야 하고(ADR-0033), 공개 화면은 ammonia 로 정화한다. 인라인 `style` 이나 임의 클래스를 허용하면 XSS 표면이 넓어지고, 테마를 바꾸면 색이 깨진다.
- **결정:**
  - 블록: `:::info|tip|warn|danger` (강조 상자), `:::center|right` (정렬) … `:::`. 여는 줄은 0칸 들여쓰기이고, 빈 줄·문서 시작·다른 상자 줄 뒤에만 올 수 있으며, 짝이 맞는 닫는 줄이 있어야 한다. 코드 펜스 안의 줄은 보지 않는다. 상자는 겹칠 수 있다.
  - 인라인: `:color[글자]{red|orange|green|blue|purple|gray}`, `:mark[글자]{yellow|green|blue|pink}`, `:size[글자]{small|large|xlarge}`. 줄을 넘지 않고, `\:` 은 문법이 아니며, 팔레트 밖 값은 글자 그대로 둔다. (값 목록은 ADR-0046 에서 늘었다.)
  - 서버는 pulldown-cmark 앞 단계(`core::directives::expand`)에서 HTML 로 펼치고, ammonia 에는 이 문법이 만드는 클래스(`callout callout-*`, `align-*`, `tc-*`, `hl-*`, `fs-*`)만 허용 목록으로 준다. 사용자가 직접 쓴 같은 이름의 클래스는 남지만 다른 클래스·속성은 지워진다.
  - 에디터는 markdown-it 플러그인(`maruDirectives`)과 ProseMirror 노드(`box`)·마크(`color`·`highlight`·`size`)로 같은 문법을 읽고 쓴다. 손실 검사에도 같은 플러그인을 쓴다.
  - 색은 테마 토큰(`--fg` 와 섞은 `color-mix`)으로 정해 밝은·어두운 테마 모두에서 대비를 지킨다.
  - 각주는 서버가 직접 번호 id(`fn-N`, `fnref-N`)로 그리고, 정화 단계는 이 형태의 id 만 남긴다.
- **대안:** 인라인 HTML(`<span style>`) — 정화와 충돌, 테마 무관한 색. 임의 색 코드(`{#ff0000}`) — 어두운 테마에서 대비가 깨진다. CommonMark generic directive 전체(`{.class #id key=val}`) — 허용 범위가 넓어 정화 규칙이 복잡해진다.
- **결과:** 원문이 Markdown 으로 남아 에이전트도 같은 문법으로 꾸밀 수 있다(CLI·MCP 그대로). 문법을 모르는 다른 Markdown 도구에서는 `:::info` 같은 글자가 보인다. 인용구 모양 변형은 아직 없다.

## ADR-0035 사진 크기는 주소 조각, 캡션은 그림 제목, 갤러리는 상자, 축소본은 렌더 때 DB 에서

- **배경:** 블로그 사진은 크기(100·75·50%)·캡션·여러 장 격자가 필요하고, 공개 화면은 업로드 때 만든 축소본(640·1280, ADR-0032)을 `srcset` 으로 써야 모바일에서 가볍다. 원문은 Markdown 이어야 하고(ADR-0033), 다른 Markdown 도구에서 열어도 그림이 깨지면 안 된다.
- **결정:**
  - 크기: 그림 주소 끝 조각 `#w75`·`#w50`(`![바다](/media/…/a.jpg#w50)`). 조각은 서버가 요청하지 않으므로 다른 도구에서도 그림이 그대로 보인다. 렌더러가 조각을 떼고 `img-w50` 클래스로 바꾼다. 정해진 값만 받는다.
  - 캡션: CommonMark 그림 제목(`![바다](a.jpg "동해 바다")`). 그림 하나만 있는 문단에 제목이 있으면 `<figure class="figure">` + `<figcaption>` 으로 그린다. 글 사이에 낀 그림은 제목을 `title` 로만 둔다.
  - 갤러리: 상자 문법에 `:::gallery` 를 더한다(ADR-0034). 공개 화면은 CSS 격자(안의 문단은 `display: contents`)로 그린다.
  - 축소본: 공개 화면이 렌더할 때 본문의 `/media/…/<id>.<ext>` 그림을 `media_by_id` 로 찾아(한 글 60장까지) `width`·`height`·`srcset`·`sizes` 를 붙인다. 원문에는 저장하지 않으므로 축소본 규칙이 바뀌어도 글을 고칠 필요가 없다. 모든 그림에 `loading="lazy" decoding="async"` 를 붙인다.
  - 정화: `srcset` 은 `/media/` 로 시작하고 안전한 글자로만 된 후보일 때만, `sizes`·`loading`·`decoding` 은 렌더러가 쓰는 값일 때만 남긴다. 사용자가 직접 쓴 다른 값은 지운다.
  - 에디터: 그림 노드에 `width` 속성, 캡션은 `title`. 그림을 고르면 「사진 크기」「캡션」 단추가 켜진다.
- **대안:** `{width=50%}` 같은 속성 문법 — 다른 도구에서 글자로 보인다. 원문에 `srcset` 을 저장 — 축소본 규칙이 바뀌면 모든 글이 낡는다. 축소본 파일 존재를 파일 시스템으로 확인 — 원본 폭을 몰라 `srcset` 에 원본을 넣을 수 없다.
- **결과:** 글 하나를 그릴 때 그림 수만큼 DB 조회가 늘어난다(SQLite 로컬 조회라 작다). RSS·관리 미리보기는 축소본 없이 그린다.

## ADR-0036 동영상·장소는 한 줄 문법, 재생기는 정화 뒤 검증된 주소만

- **배경:** 블로그 글에는 유튜브·비메오 동영상과 장소(이름·주소·지도) 블록이 자주 들어간다. 정화 단계(ammonia)에 iframe 을 허용하면 사용자가 쓴 iframe 도 남고, 주소만 걸러도 빈 `<iframe>` 이 남는다. 지도 그림은 카카오·네이버 키가 필요하다.
- **결정:**
  - 문법: 한 줄 블록 `::video[주소]`, `::place[이름]{주소}`. 상자 문법(ADR-0034)과 같은 자리 조건(앞은 빈 줄·처음·상자 줄, 뒤는 빈 줄·끝·상자 닫는 줄)을 서버와 에디터가 똑같이 본다.
  - 동영상 주소는 유튜브(`youtu.be/ID`, `youtube.com/watch?v=ID`, `shorts/`, `embed/`, `live/`)와 비메오(`vimeo.com/숫자`)만 받고, 재생기 주소는 `youtube-nocookie.com/embed/ID`, `player.vimeo.com/video/숫자` 로 바꾼다. 정규식 없이 같은 순서로 자르는 함수를 Rust(`directives::video_embed`)와 TS(`videoEmbed`)에 두고 같은 사례로 시험한다.
  - 정화 단계에는 iframe 을 넣지 않는다. 문법은 `<div class="video"><a href="재생기 주소">동영상 보기</a></div>` 로 펼치고, 정화가 끝난 HTML 에서 재생기 주소 모양이 맞는 이 상자만 iframe 으로 바꾼다(`embed_videos`). RSS 처럼 iframe 을 못 그리는 곳에서도 링크가 남는다.
  - 공개·관리 화면 CSP 에 `frame-src https://www.youtube-nocookie.com https://player.vimeo.com` 만 더한다. iframe 에는 `referrerpolicy="strict-origin-when-cross-origin"`, `loading="lazy"` 를 붙인다.
  - 장소는 키 없이 이름·주소와 네이버 지도·카카오맵 검색 링크로 그린다. 지도 그림은 Phase 4 `map` 모듈에서 사용자가 키를 넣으면 붙인다.
- **대안:** 주소만 한 줄 쓰면 자동으로 재생기(네이버 방식) — 기존 글의 유튜브 링크 문단이 갑자기 재생기로 바뀐다. ammonia 에 iframe 허용 + 속성 필터 — 잘못된 iframe 이 빈 태그로 남는다.
- **결과:** 편집 화면은 재생기 대신 카드로 보인다(편집 중 자동 재생·외부 요청 없음). 링크 카드(E12)는 서버가 외부 페이지를 읽어야 해서 HTTP 클라이언트 의존성 결정이 필요하다.

## ADR-0037 예약 발행은 상태가 아니라 시각 열, 대표 이미지는 지정 또는 본문 첫 사진

- **배경:** 블로그는 글을 미리 써 두고 정한 시각에 공개하는 예약 발행과, 목록 썸네일·공유 미리보기(`og:image`)용 대표 이미지가 필요하다. GAP_PLAN 은 `scheduled` 상태를 적었지만 `posts.status` 에는 CHECK 제약이 있고, 상태를 늘리면 모든 전이 규칙과 공개 판정이 바뀐다.
- **결정:**
  - `posts.scheduled_at`(UTC 고정 자릿수 문자열)과 `posts.cover` 열을 더한다. 상태는 그대로 초안·검토·숨김이다.
  - 예약은 글 고치기(`PostPatch.scheduled_at`)로 건다. 발행 권한이 필요하고, 아직 공개되지 않은 글에만, 지금 이후 366일 안쪽만 받는다. 빈 문자열은 취소. 공개·삭제로 바뀌면 예약을 지운다.
  - `maru serve` 가 켜질 때 한 번, 그 뒤 20초마다 `posts::publish_due` 를 부른다. 시각이 지난 글을 로컬 권한으로 발행하고 감사 기록은 `post.publish_scheduled` 로 남긴다. 서버가 꺼져 있던 동안 지난 예약은 켜자마자 발행된다. 글 하나가 실패해도 나머지는 계속하고 다음 주기에 다시 한다.
  - 관리 화면은 브라우저 `datetime-local` 값을 사이트 시간대(`tz_offset_min`)로 읽고(`clock::from_local_input`), CLI `--schedule` 은 RFC3339 와 같은 지역 시각 형식을 둘 다 받는다.
  - 대표 이미지는 이 사이트에 올린 사진 주소(`/media/…`)만 지정할 수 있고, 비우면 본문의 첫 보관소 사진을 쓴다(`posts::cover_of`). 목록은 가장 작은 축소본을, `og:image` 는 가장 큰 축소본의 절대 주소를 쓴다. 보관소에서 찾지 못한 사진은 빼서 깨진 그림을 만들지 않는다.
  - 요약을 비우면 본문 앞부분을 쓴다. 이때 표 칸은 띄어 쓰고 그림 설명(alt)은 뺀다.
- **대안:** `scheduled` 상태 추가 — 마이그레이션이 CHECK 를 바꾸려면 표를 다시 만들어야 하고 전이 규칙이 복잡해진다. 운영체제 작업 스케줄러 — 단일 바이너리 원칙(5)에 어긋난다. 외부 이미지도 대표 이미지로 허용 — 크기·축소본을 알 수 없고 외부 요청이 생긴다.
- **결과:** 예약은 서버가 켜져 있어야 그 시각에 발행된다(최대 20초 늦음). 화면에 이 점을 적었다.

## ADR-0038 첨부 파일은 다시 인코딩하지 않는 대신 화이트리스트·서명 검사·내려받기 전용

- **배경:** PDF·한글(HWP·HWPX)·오피스·압축 파일 첨부가 필요하다. 그림처럼 다시 인코딩할 수 없어서, HTML·SVG·스크립트를 문서처럼 꾸며 올리면 사이트 주소로 열리는 저장형 XSS 가 생길 수 있다.
- **결정:**
  - 그림(`media`)과 다른 `files` 표와 서비스(`services::files`)를 둔다. 보관 경로는 `files/YYYY/MM/<id>.<확장자>` 이고 이름은 경로에 쓰지 않는다. `/media/*` 는 jpg·png 만 내보내므로 첨부가 그쪽으로 새지 않는다.
  - 확장자 화이트리스트(pdf, hwp, hwpx, docx, xlsx, pptx, doc, xls, ppt, zip, txt, csv, md)와 내용 서명(`%PDF-`, ZIP `PK\x03\x04`, OLE `D0 CF 11 E0…`, 글자는 UTF-8·NUL 없음)이 둘 다 맞아야 받는다. 10MB 이하.
  - 내려받기는 `/files/<id>` 하나다. 항상 `Content-Disposition: attachment`(RFC 6266, `filename*=UTF-8''…`), 확장자로 정한 MIME, `nosniff`, `CSP: default-src 'none'; sandbox` 로 보낸다. 그림처럼 누구나 받을 수 있다(글에 링크로 붙이는 파일).
  - 파일 이름은 경로·제어 문자·`"<>|:*?` 를 지우고 120자로 줄인다(확장자는 살린다). 한글 이름은 그대로 둔다.
  - 본문에는 `[견적서.pdf (120KB)](/files/<id>)` 링크로 넣고, 공개 화면은 `/files/` 링크에 📎 표시를 붙인다. 업로드는 PostUpload, 삭제는 PostModerate 권한이다.
- **대안:** media 표에 섞기 — 폭·높이·축소본이 없는 행이 생기고 그림 전용 규칙(다시 인코딩)이 흐려진다. 바이러스 검사 — 외부 엔진이 필요하다(단일 바이너리 원칙). 첨부를 브라우저 안에서 보기(PDF inline) — 꾸민 파일이 사이트 출처로 열린다.
- **결과:** 내려받은 파일 자체의 안전(매크로 등)은 받는 사람 기기의 몫이다. 글이 지워져도 첨부는 남는다(그림과 같다). 첨부 관리 화면은 아직 없고 CLI·REST 로 목록·삭제한다.

## ADR-0039 글 틀은 기본 틀(바이너리) + 저장한 틀(DB), 이름 기준 덮어쓰기

- **배경:** 네이버 블로그의 템플릿, 그누보드의 게시판 기본 글처럼 자주 쓰는 글 모양을 불러오는 기능이 필요하다. 에이전트가 여러 번 실행해도 틀이 늘어나지 않아야 한다(원칙 3).
- **결정:**
  - 기본 틀 네 개(여행기·리뷰·공지·레시피)는 `services::templates` 상수로 두고 `builtin-*` ID 를 준다. 고치거나 지울 수 없다. 에디터 왕복 시험이 이 파일을 직접 읽어 서식 모드로 열리는지 확인한다.
  - 사용자 틀은 `post_templates` 표에 둔다. 저장은 이름 기준 upsert(같은 내용이면 그대로), 삭제는 ID 나 이름으로. 목록은 글쓰기 권한, 저장·삭제는 발행 권한이다.
  - 에디터 「틀」 메뉴: 빈 글이면 틀로 채우고, 쓰던 글이 있으면 커서 자리에 넣는다(실행 취소 가능). 「지금 글을 틀로 저장…」으로 현재 본문을 저장한다.
  - REST `GET/POST /api/v1/templates`, `DELETE /api/v1/templates/{id|이름}`, CLI `maru template list|save|delete`, 관리 화면 `/admin/templates`(세션 + CSRF)가 같은 서비스를 쓴다.
- **대안:** 게시판마다 기본 글 하나(그누보드 방식) — 블로그는 글 종류가 게시판보다 다양하다. 틀을 설정(settings) JSON 에 저장 — 감사 기록과 개별 삭제가 어색하다.
- **결과:** 게시판별 기본 틀 지정은 아직 없다(필요해지면 게시판 정책에 틀 ID 를 더한다).

## ADR-0040 원칙 7 범위: 코드·이미지·아이콘·로고는 복제 금지, 레이아웃·화면 구성은 참고 허용

- **배경:** 원칙 7은 「코드·이미지·일러스트·화면 구성」 복제를 모두 금지했다. 그래서 글쓰기 화면(네이버·티스토리), 그누보드7 창작마당 분석처럼 흔한 화면 배치·사용 흐름까지 조심스럽게 피해야 했다. 레이아웃과 기능 구조는 대부분 아이디어에 가까워 보호 대상이 아니고, 한국형 사이트는 사용자가 익숙한 배치를 따라야 쓰기 쉽다. 사용자 결정(2026-11-03).
- **결정:**
  - 금지: 특정 사이트의 코드(HTML·CSS·JS)·이미지·일러스트·아이콘·로고 복제, 한 사이트를 색·간격·장식·문구까지 통째로 옮겨 그 사이트처럼 보이게 만드는 것.
  - 허용: 레이아웃·화면 구성·사용 흐름 참고. 구현은 우리 디자인 토큰·섹션 블록으로 새로 한다.
  - 외부 자산은 그대로 MIT·CC0 등 재배포 가능한 것만, 출처는 `THIRD_PARTY.md`.
- **대안:** 화면 구성까지 금지 유지 — 익숙한 배치를 일부러 비틀게 되어 쓰기 불편해진다. 전부 허용 — 코드·자산 저작권과 부정경쟁방지법(성과물 도용) 위험.
- **결과:** CLAUDE.md 원칙 7, SPEC §8.7, `docs/proposals/universal-site.md` 문구를 맞췄다. 제품으로 배포할 때 특정 사이트와 지나치게 닮은 테마는 출시 전 검토한다.

## ADR-0041 접기 상자는 기존 상자 문법의 한 종류, 요약은 상자 안 첫 문단

- **배경:** FAQ·아코디언은 가게·기관·회사 사이트에서 흔하다(창작마당 FAQ 모듈, SPEC §8.5 「FAQ 아코디언」 블록). 별도 FAQ 모듈 대신 글·페이지 어디서나 쓰는 블록 하나로 풀고 싶다. 에디터는 지금 다른 작업이 도구 막대를 고치는 중이라 새 노드 종류를 더하기 어렵다.
- **결정:**
  - `:::details` … `:::` 를 ADR-0034 상자 종류에 더한다. **상자 안 첫 문단이 요약**(`<summary>`), 나머지가 내용이다. 첫 블록이 문단이 아니면(목록·제목·코드·상자) 요약은 「자세히」.
  - 서버는 `<details class="fold"><summary>…</summary>…</details>` 로 그린다. 요약의 인라인 서식·글자 꾸밈은 그대로 그린다. 정화 단계는 `details` 에 `fold` 클래스만, `summary` 에는 속성 없이 남긴다(`open`·이벤트 속성 제거).
  - 에디터는 같은 상자 노드(`box`, kind `details`)로 왕복한다. 상자 그룹 `details` 를 따로 두어 강조 상자 메뉴와 섞이지 않게 했다. 편집 화면은 늘 펼쳐 두고 첫 문단을 굵게 보인다. 「넣기」 단추는 도구 막대 작업이 끝난 뒤 `setBox("details", "details")` 로 연결한다.
  - FAQ 페이지 = 접기 상자를 이어 쓴 페이지. 이어진 접기는 한 덩어리처럼 붙여 보인다.
- **대안:** `:::details[질문]` 라벨 문법 — 에디터에 요약 칸이 있는 새 노드가 필요하다. FAQ 전용 모듈(분류·검색) — 지금 필요한 것보다 크다. 필요해지면 분류(C1)·검색(C5) 위에 얹는다.
- **결과:** 요약 문단은 목록 요약문(`plain_text`)에 들어가지 않는다(다른 상자와 같은 처리).

## ADR-0042 제목 앵커는 `h-` 접두 id, 목차는 사이트 설정 기준 이상일 때만, 공개 응답은 ETag 재확인

- **배경:** 긴 글에서 원하는 절로 바로 가고 절 주소를 나누는 기능이 블로그·문서형 사이트의 기본이다(창작마당 자동 목차). 지금까지 정화 단계는 각주 번호 말고 모든 id 를 지웠다. N100 목표(SPEC §14)에서 같은 화면을 반복해 받는 전송도 줄이고 싶다.
- **결정:**
  - h2~h4 에 `id="h-<슬러그>"`. 슬러그는 한글·영문·숫자만 남기고 구분은 `-`, 영문 소문자, 60자, 중복은 `-2`·`-3`, 비면 순번. 정화 단계는 제목 태그의 `h-` 접두 id 만 남긴다(사용자가 쓴 다른 id 는 여전히 지운다).
  - 모든 렌더(RSS·미리보기 포함)에 id 를 붙이고, 「이 절 주소」 링크(`heading-anchor`)는 공개 글·페이지 화면에만 붙인다.
  - 목차는 `site.toc_min_headings`(기본 3, 0 = 끔, 최대 20) 이상일 때만, 본문 위 `<details open>` 목록으로. 자바스크립트 없다. REST `PATCH /api/v1/settings`, CLI `maru site set --toc-min-headings`.
  - 공개 화면·피드·테마 자산 응답에 본문 SHA-256 기반 약한 ETag, `If-None-Match` 가 맞으면 304. 렌더 결과는 캐시하지 않는다(무효화 버그를 만들지 않는다).
- **대안:** 글마다 목차 켜기·끄기 — 글 스키마 변경이 필요하고 지금은 사이트 기준 하나로 충분하다. 렌더 결과 캐시 — 글·메뉴·설정·디자인 어느 것이 바뀌어도 무효화해야 해서 위험이 효과보다 크다.
- **결과:** 렌더 비용은 그대로다. 304 는 전송과 브라우저 다시 그리기만 줄인다.

## ADR-0043 비밀글은 「목록엔 제목, 본문은 작성자·관리자」, 비공개는 숨김 상태

- **배경:** 한국형 게시판의 비밀글(문의·상담 게시판)은 목록에 제목과 자물쇠가 보이고 본문만 막힌다. 블로그의 「비공개」는 목록에서도 사라진다. 둘을 한 플래그로 섞으면 어느 쪽도 제대로 안 된다(GAP C4, 계획서 D2).
- **결정:**
  - `posts.is_secret`. 공개 상태인 비밀글은 목록에 나오지만 서비스(`posts::public_posts_where`)가 본문·요약·대표 이미지·태그를 비워서 준다. 본문 화면·REST `GET /posts/{id}` 는 `FORBIDDEN`(`error.post_secret`, 안내 문구)이다. 글이 있다는 사실은 숨기지 않는다.
  - 읽을 수 있는 사람: 작성자(`is_own`)와 그 게시판의 관리 등급 이상 + `PostModerate`. 판정은 `posts::can_read_secret` 한 곳.
  - 피드·사이트맵·태그 목록·태그 화면에는 아예 넣지 않는다(`PublicFilter::exclude_secret`). 제목만 있는 항목은 구독자·검색엔진에 쓸모가 없다.
  - 공개 사이트는 지금 손님 Actor 로만 그린다. 그래서 비밀글 화면은 누구에게나 같은 403 이고 ETag(ADR-0042)와 섞여도 사람마다 다른 응답이 캐시되지 않는다. 공개 사이트에 회원 로그인이 붙으면 비밀글 응답은 `Cache-Control: private, no-store` 로 바꾼다.
  - 「비공개」는 새 상태를 만들지 않고 기존 숨김(`hidden`)을 쓴다. 관리 화면 발행 서랍의 공개 범위(전체 공개·비밀글·비공개)에서 비공개는 발행·예약보다 먼저 처리한다: 공개 글은 숨기고, 공개 전 글은 예약을 풀고 저장만 한다.
- **대안:** 비밀글도 목록에서 숨김 — 「비공개」와 같아져 문의 게시판을 못 만든다. 손님 비밀번호 비밀글(그누보드 손님 글) — 손님 글쓰기(회원·스팸 방지) 이후에 더한다.
- **결과:** 목록·글·REST·피드·사이트맵·태그의 누출 경로를 e2e(`e2e_taxonomy.rs`)와 서비스 테스트가 지킨다.

## ADR-0044 태그는 사이트 하나의 목록, 주소(slug)가 같으면 같은 태그

- **배경:** 블로그 태그는 게시판을 가로질러 모아 볼 때 쓸모가 있다(계획서 D3). 사람과 에이전트가 `#Rust`, `rust`, ` Rust ` 처럼 제각각 넣는다.
- **결정:**
  - `tags(name, slug UNIQUE)` + `post_tags(post_id, tag_id, position)`. 사이트에 목록 하나.
  - 정리: 앞뒤 공백·앞 `#` 제거, 안쪽 공백은 하나로. 주소는 `slug::tag`(영문 소문자). 주소가 같으면 같은 태그로 보고 **처음 만든 이름**으로 맞춘다. 한 글에 20개, 하나에 30자까지. 넣은 순서를 지킨다.
  - 태그 목록의 글 수는 보는 사람이 읽을 수 있는 공개 글만 센다(비밀글 제외). 글이 없어진 태그는 지우지 않는다. 그 화면은 `noindex`.
  - 공개 주소 `/tags`, `/tags/{slug}`. REST `GET /api/v1/tags`, `GET /api/v1/tags/{slug}`. CLI `maru tag list`, 글에는 `--tag`(여러 번)·`--clear-tags`.
- **대안:** 게시판별 태그 — 블로그를 여러 개 운영하면 같은 주제가 갈라진다. 태그 이름 바꾸기·합치기·빈 태그 정리 — 필요해지면 `maru tag` 하위 명령으로 더한다.
- **결과:** 발행 서랍의 태그 칩은 대소문자만 맞춰 겹침을 막고, 최종 정리는 서버가 한다.

## ADR-0045 `posts.category_id` 는 FK 없이, 분류 삭제는 같은 트랜잭션에서 글을 비운다

- **배경:** SQLite 는 `ALTER TABLE ADD COLUMN … REFERENCES` 는 되지만 FK 가 걸린 열은 `DROP COLUMN` 이 안 된다. 그러면 down 마이그레이션(원칙: 모든 스키마 변경에 롤백)을 쓰려면 `posts` 를 통째로 다시 만들어야 한다.
- **결정:** `category_id TEXT` 에 FK 를 걸지 않는다. 분류를 지우면 같은 쓰기 트랜잭션에서 그 분류의 글을 비우고(`category_id = NULL`), 감사 기록 diff 에 `posts_cleared` 를 남긴다. 화면은 없는 분류를 가리키는 값을 「분류 없음」으로 본다. 분류는 게시판별 한 단계, 게시판당 100개까지, 같은 주소로 다시 만들면 기존 분류를 돌려준다(멱등).
- **대안:** 테이블 재생성 마이그레이션으로 FK — 큰 테이블에서 느리고 다른 FK·인덱스·트리거를 모두 다시 만들어야 한다. 하위 분류 — 블로그 2단 분류 요청이 생기면 `parent_id` 를 더한다.
- **결과:** 정합성은 서비스 레이어가 지킨다. 분류 삭제 테스트가 이를 확인한다.

## ADR-0046 글자 크기는 숫자 단계, 색 12·형광펜 8, 꾸밈 메뉴는 고른 뒤에도 남는다

- **배경:** 크기가 「작게·크게·아주 크게」 셋, 색 6, 형광펜 4 로는 네이버·티스토리에서 넘어온 사람이 부족하다고 느꼈다. 메뉴가 한 번 고르면 닫혀 같은 글자에 여러 색을 바꿔 보기 번거로웠다. 두 서비스의 글쓰기 화면을 보기만 하고 비교했다(`docs/research/blog-editors.md` §6).
- **결정:**
  - 크기: `:size[글자]{11|13|15|16|19|24|28|30|34|38}`. 숫자는 px 단계이고 `rem` 으로 그린다(읽는 사람이 브라우저 글자 크기를 키우면 함께 커진다). 「본문」(크기 없음)이 메뉴 맨 앞이다. 테마 본문 크기는 토큰이 정하므로 16 이 본문과 같다고 보지 않는다. 예전 `small|large|xlarge` 는 글을 깨지 않도록 계속 받지만 메뉴에는 없다.
  - 색 12: `red orange ochre brown green teal blue navy purple wine pink gray`. 형광펜 8: `yellow orange green mint blue purple pink gray`. 지금처럼 `--fg` 와 섞은 `color-mix`(형광펜은 반투명)라 어두운 테마에서도 읽힌다. 임의 색(색상판·hex)은 여전히 받지 않는다(ADR-0034 대안).
  - 서식 모드의 글자색·형광펜·크기 메뉴는 고른 뒤에도 남고 눌림 표시가 바뀐다. 닫기 단추·Esc·편집 칸과 도구 막대 바깥 누르기로 닫는다. 편집 칸에서 다른 글자를 골라도 남아 있고 눌림 표시가 그 글자에 맞춰진다. Markdown 모드는 누를 때마다 문법이 한 겹 더 감싸지므로 한 번 고르면 닫는다. 문단 종류·정렬처럼 하나만 고르는 메뉴도 닫는다.
  - 마우스로 연 메뉴는 편집 칸에 포커스를 남겨 고른 글자가 계속 보인다. 키보드로 열면 지금 값 단추에 포커스가 가고 ← → Home End 로 옮긴다.
  - 툴바: 글자색·형광펜 단추 아래에 지금 색 막대, 크기 단추 옆에 지금 크기 숫자.
  - 붙여 넣은 HTML 의 `data-color|mark|size` 값도 같은 목록으로 거른다.
- **대안:** 네이버처럼 72칸 격자 + 색상판 — 테마·어두운 화면과 대비가 깨지고 사이트 색이 제각각이 된다. 크기를 em(본문 대비)으로 — 숫자가 실제 크기와 달라 「24」를 골라도 24px 이 아니다.
- **결과:** 서버(`core::directives::SPANS`)와 에디터(`syntax.ts SPAN_VALUES`) 목록이 같아야 한다. 둘 다 왕복·정화 테스트가 지킨다.

## ADR-0047 글자 서체는 정해진 넷(명조·손글씨·붓글씨·고정폭), 내장 폰트는 나눔 폰트를 줄여 이름을 바꿔 싣는다

- **배경:** 네이버·티스토리 글쓰기에는 서체 고르기가 있고, 사용자가 「폰트 고르는 건 왜 없지」라고 물었다. 그동안은 사이트 전체 서체만 디자인 토큰(`font.body` 등)으로 정했다. 방문자 PC에 없는 글꼴을 고르게 하면 대부분 기본 글꼴로 보여 의미가 없다.
- **결정:**
  - 문법 `:font[글자]{serif|pen|brush|mono}`, 클래스 `ff-*`. 다른 글자 꾸밈과 같은 허용 목록 방식(ADR-0034·0046). 「기본 서체」(없음)가 메뉴 맨 앞이다.
  - 툴바 「본문」 옆에 서체 단추. 지금 서체 이름을 보이고, 메뉴의 이름은 그 서체로 그린다. 서식 모드에서는 고른 뒤에도 남는다(ADR-0046).
  - 명조·손글씨·붓글씨는 나눔글꼴(OFL 1.1)을 내장한다. 한글 11172자 전부를 남기고 힌팅을 빼 woff2 로 줄이면 하나에 310~460KB 다. OFL 예약 글꼴 이름 때문에 변경본의 폰트 안 이름은 `Maru Serif|Pen|Brush` 로 바꾼다(`scripts/subset-fonts.py`, `THIRD_PARTY.md`).
  - `@font-face` 는 `font-display: swap`. 브라우저는 그 서체를 쓴 글자가 있는 화면에서만 받는다. 손글씨는 같은 크기에서 작아 보여 `size-adjust` 로 키운다. 파일은 `/assets/fonts/이름-번호.woff2` 이고 1년 캐시(`immutable`), 내용이 바뀌면 번호를 올린다.
  - 명조는 내장 폰트가 먼저이고, 못 받으면 PC 명조(Noto Serif KR·AppleMyungjo·바탕)로 떨어진다. 고정폭은 테마 토큰 `--font-mono`.
- **대안:** 임의 글꼴 이름 입력 — 방문자 PC에 없으면 보이지 않고, 외부 웹폰트 CDN 은 단일 바이너리·개인정보 원칙과 맞지 않는다. 자주 쓰는 2350자만 남기기 — 크기 차이가 작아(전체도 수백 KB) 드문 글자가 다른 서체로 섞이는 손해가 더 크다. 원본 TTF 그대로 — 하나에 3MB 라 바이너리와 첫 화면이 무거워진다.
- **결과:** 바이너리가 약 1.2MB 커진다. 서버·에디터 목록이 같아야 하고, e2e 가 폰트 파일·형식·캐시·라이선스 파일을 확인한다. 서체를 더하려면 OFL·예약 이름을 확인하고 같은 스크립트로 줄인다.


## ADR-0048 운영자가 서체를 올린다: 글 안 꾸밈은 slug 모양으로 받고, 파일은 받은 그대로 낸다

- **배경:** 내장 서체 넷(ADR-0047)만으로는 「우리 회사 서체」「이 블로그 서체」를 쓸 수 없다. 사용자가 「cms 내 기능으로 폰트 알아서 추가할 수 있게」를 요청했다. 계획: `docs/plans/font-upload.md`.
- **결정:**
  - 표 `fonts`(slug·이름·대체 계열·라이선스·전문 경로)와 `font_files`(굵기 100~900·기울임별 파일). 파일 보관 경로는 `fonts/{slug}/{굵기}[i]-{sha256 앞 16자}.{형식}` 이라 바뀌면 주소도 바뀌고, 공개 주소 `/fonts/{slug}/{파일}` 은 1년 `immutable` 캐시다. 라이선스 전문은 `/fonts/{slug}/LICENSE.txt`.
  - slug 규칙: 영소문자로 시작·영소문자·숫자로 끝나는 2~32자, 가운데 `-`(겹치지 않게), 내장 서체 값·토큰 이름·CSS 키워드는 예약어. 이 모양이면 CSS class·글꼴 이름·URL 조각에 그대로 써도 안전하다. CSS 글꼴 이름은 `maru-u-{slug}`(PC 에 설치된 글꼴과 겹치지 않게).
  - **글 안 꾸밈** `:font[글자]{slug}` 은 렌더가 DB 를 보지 않고 slug **모양**만 본다. 정화기는 span 의 class 를 정해진 목록 대신 `directives::filter_span_classes` 로 걸러 `ff-{slug}` 를 통과시킨다(ammonia 의 허용 클래스는 고정 목록이고 attribute_filter 뒤에 적용되기 때문). 서체를 지워도 class 는 남고 CSS 가 없어 기본 서체로 보일 뿐 글은 바뀌지 않는다. 에디터는 목록에 없는 slug 를 지우지 않고 「(지워진 서체)」로 보인다.
  - **사이트 서체** 토큰 `font.body`·`font.heading`·`font.mono` 에 올린 서체 slug 를 넣을 수 있다. 토큰 검증은 모양만, 저장할 때 서비스가 DB 에 있는지 확인한다. 토큰이 쓰는 서체는 지울 수 없다(`CONFLICT` + `maru design set --set font.body=Pretendard`).
  - 형식은 woff2·woff·ttf·otf 를 **받은 그대로** 낸다. 첫 바이트로 형식을 판정하고(확장자 무시) WOFF 머리 길이·sfnt 표 위치가 파일 안인지만 본다. 깊은 검사는 브라우저 폰트 정화기(OTS)에 맡긴다. 파일 하나 20MB, 3MB 넘으면 경고. 이 때문에 요청 본문 전체 상한을 20MB+여유로 올리고, 그림·첨부 경로의 추출 상한은 10MB 그대로 둔다.
  - 라이선스는 OFL-1.1·Apache-2.0·MIT·CC0-1.0·other(웹폰트 사용권을 직접 확인함) 중 하나 + 「웹에 내보낼 권리가 있다」 확인이 필수다. CLI 는 묻지 않고(원칙 3) `--yes` 가 그 확인이며, 없으면 다음 명령을 안내한다.
  - 다섯 경로: `services::fonts`(권한 `design.edit`, 감사 `font.add|file.add|update|file.remove|remove`), REST `/api/v1/fonts…`(파일은 `/media` 처럼 원본 바이트 + 쿼리 `weight`·`italic`), CLI `maru font add|list|show|update|remove`, 관리 화면 `/admin/fonts`, MCP 는 Phase 3. 공개 `/assets/fonts.css` 가 `@font-face` 와 `.ff-{slug}` 를 만든다.
  - 디자인 토큰과 같이 지금은 바로 반영하고, Phase 3 에 디자인 변경과 함께 changeset 으로 감싼다.
- **계획과 달라진 점:** 관리 화면 올리기는 스크립트(`fetch` 로 원본 바이트)가 필요하다. axum multipart 기능을 새로 켜지 않으려고 그림·첨부 올리기와 같은 방식을 썼다. 스크립트가 없으면 `maru font add` 를 안내한다(목록의 본문·제목 지정·떼기·지우기 단추는 폼이라 스크립트 없이 된다).
- **대안:** 렌더할 때 DB 의 서체 목록으로 허용 목록 만들기 — 렌더에 DB 가 필요해지고 저장된 HTML 이 서체 추가·삭제 때마다 낡는다. 서버에서 woff2 변환·한글 서브셋 — 새 크레이트(인코더·서브셋)가 필요해 수요를 보고 따로. 외부 웹폰트 연결 — 외부 의존(원칙 5)과 방문자 IP 가 외부로 나간다.
- **결과:** 운영자가 올린 서체가 에디터 메뉴(내장 넷 뒤 구분선)·글·사이트 전체에 쓰인다. 저장소 테스트(`crates/storage/tests/fonts.rs`)와 e2e(`crates/cli/tests/e2e_fonts.rs`)가 CLI·REST·관리 화면·공개 CSS·파일·지우기 흐름을 확인한다.

## ADR-0049 조회수는 서버가 글 화면에서 세어 메모리에 모았다가 20초마다 더한다, 감사 대상이 아니다

- **배경:** 한국형 게시판·블로그는 글과 목록에 조회수를 보인다(GAP C6). N100(SPEC §14)에서 조회마다 SQLite 에 쓰면 쓰기 잠금을 다투고, 새로고침·봇까지 세면 숫자가 뜻을 잃는다. 방문자를 가려내려면 IP 를 봐야 하는데 개인정보를 남기고 싶지 않다. CLAUDE.md 는 「모든 쓰기는 audit_log」라 조회마다 감사가 쌓이는 문제도 있다.
- **결정:**
  - 공개 글 화면(GET, 렌더 성공)에서 `services::views::ViewCounter::record` 를 부른다. 웹 계층은 연결 주소 IP·User-Agent·로그인한 사람만 넘기고, 셀지 말지는 core 가 정한다(원칙 1).
  - 같은 방문자 = SHA-256(그날의 무작위 소금 + IP + User-Agent + 글 ID). **같은 날(한국 시간) 한 번만** 센다. 소금은 메모리에만 있고 날이 바뀌면 새로 만든다. IP 원문·해시 어느 것도 DB·로그에 남기지 않는다. 기억은 하루 최대 10만 건, 넘으면 오래된 것부터 잊는다.
  - 세지 않는 것: User-Agent 가 비었거나 봇 표시(bot·crawl·spider·preview·headless·curl/ 등), 발행 권한이 있는 로그인 사용자(운영자·편집자), HEAD 요청. 전달 헤더(`X-Forwarded-For`)는 믿지 않는다(요청 제한과 같다).
  - 모은 수는 20초마다(`VIEWS_EVERY`) 한 트랜잭션으로 `posts.view_count` 에 더하고, 서버를 끌 때(강제 종료 포함) 한 번 더 더한다. 실패하면 수를 되돌려 다음에 다시 시도한다. 더할 때 `updated_at`·리비전은 건드리지 않고, 글 고치기(`update_post`)는 조회수를 덮어쓰지 않는다.
  - 화면·REST 단건·관리 목록은 「DB 값 + 아직 안 더한 수」를 보인다. 공개 목록은 DB 값(최대 20초 늦음).
  - **조회수 세기는 통계라 감사에 남기지 않는다** (CLAUDE.md 「모든 쓰기 → 감사」의 예외). 사람이 조회수를 정하는 `views::set`(게시판 관리 권한)은 `post.views.set` 으로 감사에 남긴다. REST `PUT /api/v1/posts/{id}/views`, CLI `maru post views <id> --set N`.
  - 공개 화면 표시는 `site.show_views`(기본 켬). 꺼도 세기는 계속한다. CLI `maru site set --show-views false`, REST `PATCH /settings`.
- **이전·다음 글, 관련 글 (GAP C7):** `posts::nearby` — 같은 게시판 공개 글을 `published_at, id` 순으로 바로 앞(이전 = 더 오래된)·뒤(다음 = 더 새). 비밀글·공지도 순서에 들고, 볼 수 없는 비밀글은 제목만. 관련 글은 겹치는 태그 수 → 같은 분류 → 같은 게시판 → 최신 순으로 4개, 비밀글·공지·자기 자신은 빼고, 태그가 겹치지 않는 다른 게시판 글은 넣지 않는다. 글 화면 아래, REST `GET /api/v1/boards/{board}/posts/{slug}/nearby`, CLI `maru post nearby <board> <slug>`.
- **계획과 달라진 점:** 「24시간」 대신 「같은 날」(소금을 날마다 바꾸므로 자정을 넘긴 다시 보기는 한 번 더 센다). 「304 응답 제외」는 뺐다 — ETag 비교는 렌더 뒤에 일어나고, 304 를 받는 방문은 대개 그날 이미 센 같은 방문자다. 새 인덱스는 만들지 않았다 — 기존 `posts_board_status_published` 로 충분하다.
- **대안:** 스크립트 비콘(`POST /views`) — 봇은 덜 세지만 스크립트 없는 독자가 빠지고 쓰기 끝점이 하나 는다. DB 에 (방문자 해시, 글, 날짜) 기록 — 재시작에도 정확하지만 개인정보 보관 기간·파기 규칙이 따라온다. 조회마다 UPDATE — 간단하지만 N100 에서 쓰기 잠금 경쟁.
- **결과:** 서버를 재시작하면 그날의 기억이 지워져 같은 사람이 한 번 더 셀 수 있다. 반영 주기 안에 프로세스가 죽으면(전원 차단 등) 그 사이 조회는 잃는다. 저장소 테스트(`crates/storage/tests/views.rs`)와 e2e(`crates/cli/tests/e2e_views.rs`)가 같은 사람·봇·운영자 제외, DB 반영, 화면·REST·CLI 일치, 숨김 설정, 권한을 확인한다.

## ADR-0050 사이트 검색은 FTS5 + Rust 가 자른 한글 2글자 단위, 공개 여부는 찾을 때 거른다, 검색어는 남기지 않는다

- **배경:** 한국형 게시판·블로그는 사이트 검색과 게시판 안 검색이 기본이다(GAP C5). FTS5 기본 토크나이저(`unicode61`)는 띄어쓰기로만 잘라 「제주도에서」 를 「제주」 로 못 찾고, 내장 `trigram` 은 3글자부터라 흔한 2글자 검색어(「제주」·「국밥」)가 색인을 못 쓴다. 형태소 분석기는 사전이 수십 MB 라 단일 바이너리(원칙 5)와 맞지 않는다.
- **결정:**
  - core `search` 가 자른다. NFC 정규화 → 소문자 → 한글·한자·가나 덩어리는 2글자씩 겹쳐(「제주도에서 → 제주 주도 도에 에서」) 넣고, 덩어리 끝 글자 하나를 더 넣는다(1글자 검색 앞부분 일치·구 정렬용). 영문·숫자는 낱말 그대로. FTS5 는 `unicode61 remove_diacritics 0` 으로 띄어쓰기만 자른다. 새 의존성 없음(번들 SQLite 3.51.3 에 FTS5 포함).
  - 검색어 문법: 띄어 쓴 낱말은 모두(AND), `OR`·`|` 는 어느 하나, `"구"` 는 붙은 그대로, `-낱말` 은 빼기. 100자·낱말 10개 한도. 사용자 입력을 FTS5 문법으로 넘기지 않고 모든 토막을 큰따옴표로 감싸 다시 만든다(열 이름·`NEAR`·`*` 를 직접 못 넣는다). 잘못된 검색어는 검증 오류 + 고친 예시(`hint.search_query`), 화면은 500 대신 안내.
  - 표: `search_docs`(INTEGER PK = FTS rowid, 글·페이지 하나씩 UNIQUE·FK cascade) + 내용만 든 `search_fts(title, body, tags)` + `search_state(version)`. rowid 를 표에 묶어 VACUUM 뒤에도 어긋나지 않는다. 글·페이지 쓰기(`insert_post`·`update_post`·`insert_page`·`update_page`)가 같은 트랜잭션에서 색인을 고친다.
  - 색인 버전(`INDEX_VERSION`): `Db::migrate()` 가 열 때 다르면 `BEGIN IMMEDIATE` 로 전부 다시 만든다. 자르는 규칙을 바꾸면 버전만 올린다. `maru search reindex` / REST `POST /api/v1/search/reindex` 는 사이트 관리 권한, 감사 `search.reindex`(몇 개인지만), 멱등.
  - 색인에는 상태와 상관없이 내용만 넣고, **공개 여부(발행·비밀글 아님·손님이 읽을 수 있는 게시판·공개 페이지)는 찾을 때 이어 붙여 거른다.** 서비스가 결과를 한 번 더 확인한다. 그래서 발행·숨기기·지우기·예약 발행 때 색인을 고치지 않는다.
  - 순서: bm25(제목 ×5·태그 ×3·본문 ×1), 같으면 최신. `sort=new` 는 최신순. 한 쪽 20개. 결과 토막은 본문 원문에서 찾은 말 둘레 120자, HTML 이 아닌 `{text, hit}` 조각으로 돌려주고 템플릿이 `<mark>` 로 감싼다(자동 이스케이프, `|safe` 없음).
  - 경로: `/search?q=&in=&sort=&page=`(noindex), 머리글 검색 칸(`site.show_search`, 기본 켬, 스크립트 없이 동작), `/b/{board}?q=&in=` 게시판 안 검색, REST `GET /api/v1/search`, CLI `maru search "<q>"`. 관리 화면 `/admin?q=`·REST `GET /api/v1/posts?q=`·CLI `maru post list --q` 는 권한 안에서 초안·비밀글까지.
  - **검색어는 남기지 않는다**(로그·DB·감사 어디에도). 검색은 읽기라 감사 대상이 아니다.
- **계획과 달라진 점:** 버전은 `settings` 열쇠 대신 `search_state` 표(마이그레이션 down 에서 함께 지운다). FTS 표에 `source`·`ref_id` UNINDEXED 열 대신 `search_docs` 로 rowid 를 묶었다. 관리 화면 검색은 `search(admin: true)` 대신 기존 `posts::list` 에 검색 조건(`PostFilter.search`)을 더했다 — 관리 목록의 권한 규칙(운영자는 전부, 에이전트 토큰은 제 글만)을 그대로 받는다. `maru search` 는 손님 기준(공개 화면과 같은 결과)이고, 초안까지는 `maru post list --q`.
- **대안:** 내장 `trigram` + 2글자 이하 `LIKE` 전체 훑기 — 코드가 적지만 흔한 검색이 색인 없이 돌고 순위가 없다. 형태소 분석기(lindera 등) — 정확하지만 사전이 커서 단일 바이너리가 무거워진다. 공개 글만 색인 — 발행·숨기기마다 색인을 고쳐야 하고 관리 검색을 따로 만들어야 한다.
- **결과:** 낱말 경계를 넘는 구는 안 맞는다(「제주 도」 ≠ 「제주도」), 띄어쓰기가 다르게 쓰인 글은 못 찾을 수 있다 — 필요하면 띄어쓰기를 뺀 사본 열을 더하고 버전을 올린다. 글 1만 개(디버그 빌드) 다시 만들기 15.3초, DB 41MB → 96MB(색인이 본문 글자의 약 4배), 1만 건이 걸리는 검색 0.32초(`crates/storage/tests/search.rs` 의 `#[ignore]` 측정). 저장소 테스트와 e2e(`crates/cli/tests/e2e_search.rs`)가 한글 2글자·문법·순위·범위, 비밀글·초안·숨김·지운 글·못 읽는 게시판 제외, 고친 글 반영, 다시 만들기 멱등·권한, 화면·REST·CLI 일치, 이상한 입력, 숨김 설정을 확인한다.

## ADR-0051 회원 가입은 기본 꺼짐·같은 답·1회용 메일 링크, 편지는 보낼 편지함을 거쳐 지금은 파일로만 보낸다

- **배경:** 게시판·커뮤니티는 손님 가입·메일 인증·비밀번호 찾기·내 정보가 기본이다(GAP M1·M2·M3). 지금까지는 운영자 로그인만 있었다. 메일을 보내려면 SMTP(TLS) 클라이언트가 필요한데 새 의존성(lettre 와 TLS 묶음)은 사용자 승인 대상이다.
- **결정:**
  - 설정 `signup`(`off`·`open`, **기본 off**) · `signup_verify`(기본 true). 꺼지면 `/signup` 은 404, 머리글 「내 계정」 도 숨긴다. 바꾸려면 회원 관리 권한.
  - **같은 답:** 가입·비밀번호 찾기는 이메일이 이미 있든 없든 같은 화면을 준다. 이미 있는 주소로 가입하면 그 주소로 「이미 가입돼 있다·비밀번호 찾기 링크」 편지를 보낸다. 닉네임은 2~20자, NFC, 대소문자 무시 유일(DB 인덱스), `@<>"\` 와 예약어(운영자·관리자·admin 등) 앞머리 금지 — 닉네임 겹침은 드러나도 된다.
  - 링크: `login_tickets` 에 목적(`login`·`verify`·`reset`)을 더해 같은 표를 쓴다. 서버가 만든 32바이트 값, SHA-256 해시만 저장(ADR-0009), 한 번만, 인증 24시간·재설정 60분. **GET 은 확인 화면만, POST 가 소모한다**(메일 미리보기·백신이 링크를 먼저 열어도 쓰이지 않게). 인증·재설정이 끝나면 바로 로그인시키고, 재설정·비밀번호 변경·비활성·역할 변경은 그 회원의 세션을 모두 끊는다.
  - 인증 전 로그인은 거부하고 인증 편지를 다시 쌓는다(10분에 한 통). 기존 회원은 마이그레이션에서 인증된 것으로 채운다.
  - **보낼 편지함 `mail_outbox`:** 편지는 쓰기와 같은 트랜잭션에서 쌓는다(`idem_key` UNIQUE — 같은 주소·같은 종류는 10분 창마다 한 통). 서버가 5초마다 최대 20통 배달, 실패는 5번까지 다시, 그 뒤 `failed` 로 보관. 배달 기록은 감사 대상이 아닌 시스템 기록(`Store::update_mail`). 본문은 메시지 키(`mail.{kind}.subject|body`).
  - 전송은 core 의 `Mailer` 트레이트. 지금 구현은 `FileMailer`(storage) 하나 — `데이터/mail/{시각}-{id}.eml`(RFC 5322, 제목 RFC 2047). `serve` 가 시작 JSON·안내에 「편지는 파일로만 남는다」 를 알린다. SMTP 는 lettre 승인 뒤 같은 트레이트로 더한다.
  - 편지 본문에는 1회용 링크가 있어 **로컬 운영자만** 본다(`maru mail list|show|send`). REST·에이전트 토큰으로는 못 읽는다. 감사에는 링크 값이 남지 않는다.
  - 탈퇴는 지우지 않고 익명화: 이메일 `withdrawn+{id}@invalid`, 닉네임 「탈퇴한 회원 #xxxxxx」, 비밀번호·역할·세션·링크 삭제, `withdrawn_at`. 쓴 글은 남는다. 사이트 운영자(owner)는 탈퇴하지 못한다.
  - 회원 관리(member.manage): REST `GET /api/v1/members`·`GET|PATCH /members/{id 또는 이메일}`(status·role), CLI `maru member list|show|disable|enable|role`. 역할은 `member`·`editor`·`admin` 중 하나, `admin` 을 주려면 사이트 관리 권한. 운영자·자기 자신·탈퇴한 회원은 바꾸지 못한다. 실제로 바뀐 것만 감사.
  - 화면: 테마 틀 `account.html`(로그인·가입·찾기·재설정·인증·안내)·`me.html`, 스크립트 없이 동작. CSRF 는 관리 화면과 같다(로그인 전 `maru_csrf` 쿠키 + 폼 값, 로그인 뒤 세션 값). 계정 화면은 `no-store`·`no-referrer`·noindex. 공개 페이지는 계속 손님으로 렌더해(ETag 유지) 머리글은 고정 링크 「내 계정」 만 둔다. POST `/login`·`/signup`·`/forgot`·`/reset/*`·`/verify/*`·`/me/password`·`/me/withdraw` 는 요청 제한 `Login` 칸(분당 10).
- **계획과 달라진 점:** 없음. MCP 툴은 Phase 3.
- **대안:** 가입 기본 켬 — 설치 직후 스팸 가입에 열린다. 링크 GET 으로 바로 소모 — 메일 미리보기가 먼저 써 버린다. 편지를 요청 안에서 바로 보내기 — SMTP 가 느리거나 죽으면 가입이 실패하고 재시도가 없다. 탈퇴 시 행 삭제 — 글·감사 기록의 작성자가 끊긴다.
- **결과:** 지금은 메일이 실제로 나가지 않는다(파일만). 운영 사이트는 SMTP(S5) 승인 전까지 운영자가 `maru mail list` 로 링크를 건네야 한다. 캡차는 M10, 댓글·스크랩 마이페이지는 M5·M7 뒤. 저장소 테스트(`crates/storage/tests/members.rs`)와 e2e(`crates/cli/tests/e2e_members.rs`)가 가입 꺼짐 404, CSRF 없는 가입 거부, 인증 전 로그인 거부, 편지 파일 생성, GET 확인·POST 소모·재사용 거부, 닉네임 변경 DB 반영, 세션 폼에 폼 CSRF 값 거부, REST·CLI 목록 일치, 권한 없는 토큰 거부, 비활성 → 세션 끊김, 감사에 링크 값 없음을 확인한다.

## ADR-0052 댓글은 따로 된 표·한 단계 답글·평문, 비회원은 이름+비밀번호, 확인 질문은 외부 서비스 없이 한글 셈 문제

- **배경:** 게시판·블로그·커뮤니티에는 댓글·대댓글·승인 큐가 기본이고(GAP M5), 한국형 게시판은 비회원이 이름·비밀번호로 쓰는 경우가 많다(M6). 손님 입력을 받으려면 스팸을 막을 캡차가 있어야 하는데(M10), reCAPTCHA 같은 외부 서비스는 단일 바이너리·외부 서비스 없음(원칙 5)과 방문자 정보 외부 전송 문제가 있다. 공개 글 화면은 손님으로 렌더해 ETag/304 를 지킨다(ADR-0051).
- **결정:**
  - 표 `comments`(글 FK cascade, 뿌리 `parent_id`, 누구에게 답했는지 `reply_to_id`, 상태 published·pending·hidden·spam·deleted, 작성자 FK SET NULL 또는 손님 이름+argon2id 비밀번호 해시, CHECK 로 손님 ⇔ 이름·해시). 글 표(`posts`)에 kind 를 더하지 않는다 — 목록·검색·피드·주소 쿼리마다 조건이 붙는다.
  - 깊이는 댓글 + 답글 한 단계. 답글에 답하면 같은 뿌리 아래 붙고 「@이름」 이 보인다. 본문은 평문 2000자, 줄바꿈 유지, 템플릿 자동 이스케이프(마크다운·HTML·링크 자동 변환 없음).
  - 게시판 정책 `comment`(기본 `member`, `guest`·`none`·역할) · `comment_approval`(`off`·`guest`·`all`, 기본 `guest`). 숨긴 글·초안에는 댓글이 안 달린다. **에이전트 토큰은 댓글을 쓰지 못하고 관리만 한다** — 에이전트가 사람 행세를 하지 않게.
  - 비회원: 이름 2~20자(회원 닉네임과 같은 규칙·예약어 금지) + 비밀번호 4자 이상. 고치기·지우기는 그 비밀번호로. IP 는 저장하지 않는다.
  - 지우기는 본문을 비우는 소프트 삭제. 살아 있는 답글이 있으면 「삭제된 댓글입니다」 자리만 남기고, 없으면 화면에서 빠진다. `updated_at` 은 **본문을 고친 때만** 바뀐다(「· 고침」 표시) — 승인·숨김 같은 상태 변경은 감사에만 남는다.
  - CSRF: 글 화면은 손님 렌더라 화면마다 토큰을 둘 수 없다. 세션 쿠키 SameSite=Lax + `Sec-Fetch-Site`·`Origin` 같은 출처 확인으로 막는다. 고치기·지우기 화면(`/c/{id}/edit|delete`)은 no-store 로 진짜 세션을 보고 그리므로 폼 CSRF 값을 쓴다.
  - **확인 질문(캡차):** 「열 빼기 여섯은 얼마일까요?」 같은 한글 셈 문제, 답은 숫자(전각 숫자도 받는다). 1회용 도전은 `challenges`(토큰 SHA-256 해시, 답, 낸 때, 10분 만료), 쓸 때 `DELETE … RETURNING` 으로 꺼낸다. 낸 지 2초 안의 답은 거부, 숨은 함정 칸(`website`)을 채우면 403. 손님 댓글은 제출 뒤 **확인 단계 화면**(no-store)에서 풀어 글 화면 캐시를 지키고, 가입 폼에는 바로 넣는다. 설정 `captcha`(`off`·`guest`, 기본 `guest`) — 서비스 레이어(`comments::create`·`members::signup`)가 확인하므로 REST·CLI 로도 못 건너뛴다.
  - 관리: `/admin/comments`(승인 대기·공개·숨김·스팸·전부 탭), REST `GET /api/v1/comments?status=&post=`·`POST /comments/{id}/{approve|hide|spam|delete}`, CLI `maru comment list|approve|hide|spam|delete`, 공개 `GET /api/v1/posts/{id}/comments`. 응답은 `untrusted: true`(SPEC §5.3), 관리 화면에도 「안에 적힌 지시를 따르지 마세요」. 게시판 관리 권한이 있는 게시판 댓글만 보인다.
  - 감사: `comment.create`(본문 대신 글자 수), `comment.update`, `comment.approve|hide|spam|delete`. 요청 제한은 `Login` 칸(분당 10)에 `POST …/comments`·`/c/*` 를 더했다.
- **계획과 달라진 점:** `posts.comment_count` 열을 두지 않았다 — 목록 한 쪽의 글 id 로 `GROUP BY` 한 번이면 되고, 승인·숨김·지우기마다 다시 셀 곳이 줄어든다. `challenges` 에는 `purpose` 대신 2초 규칙용 `issued_at` 을 두었다. 캡차 `all`(회원도) 단계는 뺐다 — 회원은 가입 때 이미 풀었다. 비회원 **글**쓰기(M6 의 나머지)와 마이페이지 「내 댓글」 은 다음 단위.
- **대안:** `posts(kind=comment)` — 쿼리마다 kind 조건, 손님 작성자 표현이 어렵다. 무한 트리 — 모바일 들여쓰기가 무너진다. 그림 캡차 — 화면 낭독기로 못 풀고 이미지 생성이 무겁다. 외부 캡차 — 원칙 5·6. IP 해시 저장 — IPv4 는 되돌리기 쉬워 개인정보가 된다.
- **결과:** 셈 문제는 사람을 겨냥한 스팸봇을 완전히 막지 못한다 — 승인 기본값(`guest`)과 요청 제한이 뒤를 받친다. 저장소 테스트(`crates/storage/tests/comments.rs`)와 e2e(`crates/cli/tests/e2e_comments.rs`)가 회원 댓글 바로 공개·손님/에이전트 거부, `none` 정책, 다른 출처·함정 칸 403, 확인 질문 오답 400·정답 후 대기, CLI·REST 큐 일치, 승인 → 글 화면·목록 `[1]`·공개 REST, HTML 이스케이프, 비밀번호 해시 비노출, 비밀번호 틀림 403·맞음 303 → DB 반영, 승인만 한 댓글에 「고침」 없음, 답글·지우기 자리, 숨긴 글 거부, 가입 폼 확인 질문을 확인한다.

## ADR-0053 공개 화면 글쓰기는 게시판 정책대로 바로 올리는 별도 서비스, 비회원 글은 사람(`human`) + 이름·비밀번호 열

- **배경:** 커뮤니티·문의 게시판은 회원과 손님이 공개 화면에서 글을 쓴다(GAP M6 나머지). 지금까지 글은 관리 화면·CLI·REST 로만 썼고, 관리 경로는 초안 → 발행(`post.publish` 권한)이라 회원에게 열면 관리 글까지 발행할 수 있게 된다. `posts.actor_type` CHECK 에는 손님이 없고, SQLite 는 CHECK 를 바꾸려면 FK 가 걸린 `posts` 를 통째로 다시 만들어야 한다.
- **결정:**
  - core `board_posts::write`·`edit`·`remove`(+ `editable`·`editable_at`·`rules`). 게시판 정책 `write`(최소 역할, `guest` 면 손님도)가 「자기 글을 바로 올릴 권한」 이다. 발행 권한은 필요 없다. 공지·예약·대표 이미지·주소 지정은 관리 경로에만 있다.
  - 새 정책 `write_approval`(`off`·`guest`·`all`, 기본 `guest`). 대기 글은 기존 상태 `pending`, 운영자가 `maru post publish`·관리 화면 「지금 발행」 으로 올린다(`publish` 가 `pending` 을 받는다). 댓글 승인과 같은 형이라 `CommentApproval` 을 `Approval` 로 이름을 바꿨다.
  - **에이전트는 이 경로를 쓰지 못한다**(초안 → 발행·changeset, 원칙 4). 사람(회원)·손님·로컬만.
  - 비회원 글: `posts.guest_name`·`guest_pw_hash`(argon2id) 열을 더하고 `actor_type` 은 `human`(사람이다), `author_id` 는 비운다. 이름·비밀번호 규칙은 비회원 댓글과 같다. 비밀번호 해시는 직렬화하지 않는다(REST·CLI·감사 diff 에 없음). 비회원 비밀글은 받지 않는다(읽을 방법이 비밀번호 화면뿐이라 다음 단위).
  - 손님 글은 누구의 「자기 글」 도 아니다(`is_own`): 비밀번호나 게시판 관리 권한으로만 고친다. 회원은 자기 글, 관리자는 전부(기존 `authorize_post`).
  - 화면: `/write/{board}`(새 글 — `/b/{board}/{post}` 와 겹치지 않게 게시판 주소 밖), `/b/{board}/{post}/edit|delete`. 모두 no-store·noindex, 진짜 세션으로 렌더, 스크립트 없이 동작. 회원은 세션 CSRF, 손님은 로그인 전 CSRF 쿠키 + 확인 질문(폼 안, 60분) + 함정 칸 + 같은 출처 확인. 요청 제한 `Login` 칸에 이 POST 들을 더했다. 본문은 마크다운(관리 글과 같은 렌더러·ammonia).
  - 표시: 게시판 정책 `write` 가 `guest`·`member` 인 게시판만 목록에 「글쓰기」 단추와 글쓴이(회원 닉네임·손님 이름 + 「비회원」), 글 화면에 「목록·고치기·지우기」. 블로그처럼 운영자가 쓰는 게시판은 지금 그대로다. 공개 화면은 계속 손님으로 렌더한다(ETag 유지) — 누가 고칠 수 있는지는 누를 때 본다.
  - 감사: `post.write`(새 글), `post.update`, `post.delete`. 리비전은 관리 글과 같다.
- **계획과 달라진 점:** 새 글 주소를 `/b/{board}/write` 대신 `/write/{board}` 로 했다 — 슬러그가 `write` 인 글과 겹친다. 서비스 이름을 `posts::submit` 대신 `board_posts::write` 로 했다 — `posts::submit` 은 이미 초안 → 검토 요청이다.
- **대안:** 회원에게 `post.publish` 를 주기 — 관리 글·남의 초안까지 발행할 수 있다. `actor_type` 에 `guest` 추가 — `posts` 다시 만들기(FK 끄고 12단계) 위험에 비해 얻는 것이 없다. 공개 글쓰기용 REST 끝점 — 사람·손님 전용이라 토큰 주체(에이전트)가 쓸 일이 없다.
- **결과:** 첨부·사진 올리기·서식 도구는 아직 없다(마크다운 칸만, M4 업로드 권한과 다음 단위). 관리 화면 글 목록·편집기에 손님 이름이 아직 안 보인다. 저장소 테스트(`crates/storage/tests/board_posts.rs`)와 e2e(`crates/cli/tests/e2e_board_write.rs`)가 회원 글 바로 공개·남의 글 거부·글쓴이 고치기·지우기, `editor` 정책에서 회원 거부, 손님은 확인 질문·비밀번호·비밀글 거부·승인 대기 → 발행, `all` 승인에서 관리자는 바로, 에이전트 거부, 해시 비노출, 다른 출처·함정 칸·CSRF 없음 403, 틀린 답 400(적은 내용 유지), 목록·글 화면 손님 이름, 정화된 본문, 비밀번호로 고치기 → DB, 지우기 → `deleted`, 손님은 회원 게시판에서 로그인으로, 감사 3건을 확인한다.

## ADR-0054 게시판 목록 형태는 `boards.layout` 열(빈 값 = 종류 기본값), 새 글·대체 타일·떠 있는 단추는 스크립트 없이

- **배경:** 한국형 게시판은 같은 글 목록을 게시판마다 번호 목록·카드·갤러리·웹진으로 보인다(GAP C8). 지금까지는 한 가지(그림 + 요약, 웹진)뿐이었고, 그림 없는 글·새 글·긴 글에서 목록으로 돌아가기(C15)가 없었다.
- **결정:**
  - `boards.layout` 열(`list`·`webzine`·`card`·`gallery`, 빈 값이면 종류 기본값: blog → webzine, gallery → gallery, 나머지 → list). 권한이 아니라 표현이라 정책 JSON 에 넣지 않았다. core `BOARD_LAYOUTS`·`Board::effective_layout()`, `NewBoard`·`BoardPatch` 의 `layout`(빈 값은 기본값으로 되돌리기), 모르는 값은 `error.board_layout`. REST 는 같은 입력 타입이라 저절로, CLI `board create|update --layout`·`board show` 에 형태.
  - 공개 JSON: `board.layout`(실제로 쓸 형태), 글마다 `is_new`(발행 24시간 안)·`initial`(제목 첫 글자)·`number`(게시판 목록에서 전체부터 거꾸로, 공지 제외). 형태 이름은 코어가 정하고 모양은 테마(`_list.html`)가 그린다. 첫 화면·태그 목록은 게시판이 없어 웹진.
  - 표 목록은 번호·제목(분류·댓글 수·새 글)·글쓴이(공개 글쓰기 게시판만)·날짜·조회, 좁은 화면에서는 두 줄. 카드·갤러리는 격자, 그림 없는 글(과 비밀글)은 분류 이름(없으면 제목 첫 글자) 타일 — 자산 파일 없이 CSS 만. 웹진이 아닌 형태는 넓은 화면(`wrap wide`).
  - 새 글 표시는 「N」 + 숨은 글자 「새 글」. 공개 화면 ETag 가 본문 해시라 24시간이 지나면 응답이 저절로 바뀐다(캐시 무효화가 따로 필요 없다).
  - 글 화면 오른쪽 아래 「맨 위」(`#main`)·「목록」 단추: `position: fixed`, 스크립트 없음, 인쇄 때 숨김.
- **대안:** 정책 JSON 에 넣기 — 마이그레이션은 없지만 정책의 뜻이 흐려지고 정책 검증과 섞인다. 테마마다 형태를 따로 — 에이전트가 「갤러리로 바꿔」 를 테마와 상관없이 할 수 없다. 기본 대체 그림 파일 — 사이트마다 안 어울리고 자산 출처를 관리해야 한다.
- **결과:** 새 글 기간(24시간)은 상수다. 관리 화면 게시판 설정 폼에는 아직 형태 칸이 없다(관리 화면 전체 단위 S4). 저장소 테스트(`board_layout_defaults_and_validation`)와 e2e(`crates/cli/tests/e2e_board_layout.rs`)가 종류 기본값, CLI → DB 열, 갤러리 격자·대체 타일, 카드, 모르는 값 거부(DB 그대로), 빈 값으로 되돌리기, 번호 3·2·1, 24시간 지난 글은 새 글 표시 없음, 글 화면 떠 있는 단추, 감사 2건을 확인한다.

## ADR-0055 리비전 비교는 직접 만든 줄 단위 LCS, 되돌리기·이동·복사는 기존 쓰기 규칙 그대로, 일괄은 글마다 따로

- **배경:** 리비전은 저장만 되고 어느 경로로도 보이지 않았다(GAP C12). 글을 다른 게시판으로 옮기거나 복사하는 방법, 관리 화면에서 여러 글을 한 번에 다루는 방법도 없었다(C11).
- **결정:**
  - core `diff` 모듈: 줄 단위 LCS(같음·더함·뺌), 앞뒤 같은 줄은 표를 만들지 않고, 가운데 양쪽 줄 수의 곱이 400만을 넘으면 「통째로 바뀜」(`coarse`). 새 의존성 없음.
  - `posts::revision`·`compare`(리비전 → 지금 글)·`revert`: 되돌리기는 그 리비전의 제목·본문으로 고치는 것이라 권한·상태 규칙이 `update` 와 같고(지운 글 거부), 리비전이 하나 더 쌓인다. 이미 같으면 그대로(멱등). 다른 글의 리비전은 없는 것으로(`error.revision_not_found`, 다음 명령 `maru post revisions`). 감사 `post.revert` 의 diff 에 리비전 id.
  - `posts::move_to`: 원래 게시판에서 고칠 권한 + 새 게시판 쓰기 권한(정책 `write`·게시판 범위). 분류는 새 게시판 것만(생략하면 비움), 슬러그가 겹치면 `-2`. 글 id 가 그대로라 댓글·조회수·리비전·검색 색인이 따라간다. 감사 `post.move`.
  - `posts::copy_to`: 새 게시판에 **초안**(`create_draft` 를 그대로 부른다). 글쓴이는 복사한 사람, 댓글·조회수·공지는 가져가지 않는다.
  - `posts::bulk`(1~100개, 같은 id 는 한 번): `publish`·`hide`·`delete`·`restore`·`move`. 글마다 기존 서비스를 따로(각자 트랜잭션) 부르고 `[{id, ok, post | error{code, message}}]` 를 돌려준다.
  - 경로: REST `GET /posts/{id}/revisions`, `GET /posts/{id}/revisions/{rev}`(비교), `POST …/revert`, `POST /posts/{id}/move`·`copy`, `POST /posts/bulk`. CLI `post revisions|diff|revert|move|copy|bulk`. 관리 화면 `/admin/posts/{id}/revisions`(목록 + 고른 리비전과 지금 비교, 기본은 「지금」 바로 앞 것, 되돌리기 단추), 편집기에 「리비전 보기」·다른 게시판으로 옮기기·초안으로 복사, 글 목록에 고르기 칸 + 일괄 바. 고르기 칸은 `pick.<글 id>` 라 같은 이름이 여러 번 오지 않아 지금 폼 추출기로 받는다(새 의존성 없음).
- **대안:** `similar` 크레이트 — 의존성 승인이 필요하고 글 본문 크기에서는 직접 구현으로 충분하다. 일괄을 한 트랜잭션으로 — 글마다 권한·상태가 달라 하나만 막혀도 전부 실패하고 무엇이 문제인지 알기 어렵다. 이동을 지우고 새로 쓰기로 — 주소·댓글이 끊긴다.
- **결과:** 페이지 리비전 화면은 아직 없다(같은 `diff` 로 다음에). 옮긴 글의 옛 주소는 404 다(주소 바꿈 기록은 SEO 단위). 저장소 테스트(`crates/storage/tests/post_admin.rs`)와 core `diff` 단위 테스트, e2e(`crates/cli/tests/e2e_post_admin.rs`)가 비교 줄·되돌리기 → DB·리비전 +1·멱등·남의 글·다른 글 리비전·지운 글 거부, 이동 슬러그 겹침·분류 비움·공개 주소 바뀜·옛 주소 404, 회원의 스태프 게시판 이동 거부, 복사는 초안, 일괄 일부 성공(CONFLICT·NOT_FOUND)·중복 id·빈 목록 거부, 관리 화면 리비전 비교 표시·CSRF 없는 되돌리기 거부·되돌리기 → DB, 목록에서 두 글 옮기기 → DB 를 확인한다.

## ADR-0056 답변글은 parent_id·thread_id·thread_path 세 칸, 게시판 정책 `reply` 로 연다

- **배경:** 문의·자유 게시판에 원글 아래 이어지는 답변글(계층)이 없었다(GAP C9). SPEC 은 정렬 문자열 하나(`wr_reply` 식)를 버리고 `parent_id` + `thread_path` 를 정했다.
- **결정:**
  - `posts` 에 `parent_id`(바로 위 글, FK)·`thread_id`(맨 위 글, 맨 위 글 자신은 비움)·`thread_path`(형제 순서 `0001.0002.`, 깊이마다 다섯 글자)·`thread_owner`(맨 위 글을 쓴 회원) 네 칸. 깊이는 `thread_path` 길이로 세고 최대 5. 형제 순서는 트랜잭션 안에서 위 글의 답변 수(상태 무관)로 정해 지워도 번호가 겹치지 않는다.
  - 목록(`list_published`)은 스레드끼리 맨 위 글 발행순, 스레드 안에서는 `thread_path` 순. 화면은 깊이만큼 들여 쓰고 ㄴ 모양 표시, 목록 번호는 모든 글에 그대로 센다.
  - 게시판 정책 `reply`(최소 역할, `none` 이면 받지 않음). 정책 JSON 의 serde 기본값이 `none` 이라 기존 게시판은 닫혀 있고, 새 qna 게시판만 `editor`. 알 수 없는 역할은 `error.board_policy_role`.
  - `posts::reply(parent, ReplyInput)` — 관리 경로(초안 → 발행). `create_draft` 와 같은 내부 함수에 위 글을 넘긴다. 공개 화면은 `board_posts::write` 의 `reply_to` 로, 글쓰기 권한(`write`)과 답변 권한(`reply`)을 둘 다 본다. 둘 다 `reply_spot` 하나가 위 글(같은 게시판·발행됨·읽을 수 있는 비밀글)·정책·깊이를 검사한다. 답변 폼을 열기 전 검사는 `board_posts::reply_target`.
  - 분류는 위 글을 따르고, 위 글이 비밀글이면 답변도 비밀글. 비밀 답변은 쓴 사람·관리자에 더해 맨 위 글을 쓴 회원(`thread_owner`)도 읽는다 — 문의 게시판의 기본 흐름.
  - 원글을 지워도 답변은 남는다. 답변 화면의 「답변한 글」 링크는 위 글이 공개일 때만.
  - 경로: REST `POST /posts/{id}/reply`, CLI `post reply <id> --title --body|--from [--publish]`·`board update --reply`, 공개 화면 글 화면 「답변」 단추(정책이 `guest`·`member` 이고 공개 글쓰기 게시판일 때) → `/write/{board}?reply=<글 id>`(제목 `RE: …`, 분류 칸 없음), 관리 편집기 「답변 쓰기」 → 답변 초안을 만들고 그 편집 화면으로.
- **대안:** 정렬 문자열 하나 — SPEC 이 버렸다. 중첩 집합 — 쓰기가 비싸다. `NewPost` 에 `parent` 칸 — 기존 리터럴이 많이 바뀌고 답변이 아닌 글에도 칸이 생긴다. 답변 권한을 쓰기 권한과 같게 — 공지·갤러리에도 답변이 열린다.
- **결과:** MCP 툴은 Phase 3. 원글이 지워진 답변에 따로 표시는 없다. 저장소 테스트(`crates/storage/tests/replies.rs`)가 qna 기본 정책·스레드 순서·순서 경로·분류 상속, 닫힌 게시판·초안·깊이 한도·회원 거부, 감사 기록, 비밀 질문의 답변을 질문자만 읽기, 공개 화면 회원 답변 → DB·닫으면 폼 거부·알 수 없는 역할 거부를, e2e(`crates/cli/tests/e2e_replies.rs`)가 CLI 답변 → DB 순서 경로·닫힌 게시판 거부와 다음 명령·정책 변경·목록 들여쓰기·답변 화면 위 글 링크·답변 단추·손님은 로그인으로를 확인한다.
