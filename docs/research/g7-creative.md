# 그누보드7 창작마당 전수 조사 — Maru 에 필요한 것 고르기

> 조사일 2026-11-03. 대상 `https://sir.kr/g7-creative` 전체 58개(모듈 18 · 플러그인 20 · 테마 18 · 팁 2).
> 방법: 내장 브라우저로 목록 5쪽과 58개 상세 페이지 본문을 **읽기만** 했다(로그인·댓글·다운로드 없음). 코드·저장소는 열지 않았다.
> 원칙 7(2026-11-03 개정, ADR-0040): 특정 사이트의 코드(HTML·CSS·JS)·이미지·일러스트·아이콘·로고는 복제하지 않는다. 레이아웃·화면 구성·사용 흐름은 참고해도 되지만, 한 사이트의 색·간격·장식·문구까지 통째로 옮겨 그 사이트처럼 보이게 만들지는 않는다. 이 문서는 기능·흐름만 적었고 코드는 열지 않았다. 구현은 Maru 의 디자인 토큰·블록·모듈로 새로 한다.
> 함께 볼 문서: `docs/research/gnuboard7.md`(코어 소스 분석), `docs/GAP_PLAN.md`(남은 기능 표), `docs/SPEC.md`.

## 0. 요약

1. **작성자 분포가 한쪽으로 쏠려 있다.** 58개 중 35개가 한 제작자(「Glitter」 계열)의 업무형 모듈·시드 템플릿, 8개가 다른 한 제작자(「WC」 계열)의 블로그·소형 커뮤니티용 플러그인 묶음이다. 나머지는 쇼핑몰 템플릿·결제·상담 연동·설치 도구.
2. **블로그·커뮤니티 운영자가 실제로 찾는 것**(조회수·추천 기준 상위)은 소셜 로그인, 커뮤니티 템플릿, 홈 위젯·2단 메뉴, 포럼·웹진·위키 게시판, 에디터 보강(링크 카드·SNS 임베드·붙여넣기), 자동 목차, 글꼴 바꾸기, 공감 버튼이다. 업무형(LMS·CRM·정책 엔진·작업 관리)은 조회는 있으나 추천·댓글이 적다.
3. **Maru 와 비교하면** 대부분은 이미 `GAP_PLAN.md` 단위 6~15 에 들어 있다(분류·태그·공지·검색·회원·댓글·반응·위젯·통계·소셜 로그인·2단계 인증). 창작마당에서 **새로 보인 것**은 ① 제목 앵커 + 자동 목차, ② 접기(아코디언) 블록 = FAQ 의 바탕, ③ 공개 응답 조건부 캐시, ④ 위키 링크, ⑤ 포럼형 게시판(최근 활동순·답변 채택·잠금), ⑥ 웹진 대체 썸네일·새 글 표시, ⑦ 사이트 글꼴 올리기, ⑧ 광고 자리·상담 버튼, ⑨ 소셜 로그인의 「같은 이메일이라고 합치지 않는다」 정책이다.
4. **G7 생태계의 약점이 Maru 의 강점이 된다.** 상세 페이지 절반 이상이 「설치 후 페이지 로드 오류가 발생하는 경우」 절을 따로 둔다(캐시·빌드 산출물·의존 확장 순서 문제). Maru 는 단일 바이너리 + 내장 테마라 이 문제가 구조적으로 없다. 반대로 「코어를 고치지 않는 확장」은 G7 이 잘하는 점이고 Maru 는 Phase 2 모듈 시스템 전이라 아직 없다.

## 2. 공통 패턴 (여러 항목에서 반복된 것만)

1. **게시판의 재해석이 확장의 대부분이다.** 웹진·포럼·위키·지식·디렉터리·에디토리얼·Q&A 가 전부 「같은 게시판 데이터 + 다른 목록·정렬·읽기 화면」이다. → Maru 는 `boards.kind` 와 컬렉션 일반화(ADR-0019)로 이미 이 방향. 별도 테이블보다 **목록 형태·정렬·읽기 옵션**을 게시판 설정으로 둔다.
2. **긴 글 읽기 보조**: 자동 목차(15), 지식 템플릿의 목차·읽기 진행(43), 에디토리얼의 본문 폭(24). 블로그·문서형 사이트 공통.
3. **빈 상태 원칙**: 콘텐츠가 없으면 가짜 글·이미지 대신 빈 상태(24·34·43). 「백엔드가 주지 않는 의미를 화면이 지어내지 않는다」(34).
4. **외부 서비스 정보 보호**: 링크 카드 정보 저장·정리(35), 사설 주소 차단(56), 회원 정보를 외부 상담 서비스로 보낼 때 고지 필요(10 의 댓글 지적), 동의 전 외부 리소스 차단(29).
5. **멱등·재시도·실패 보관함**: 알림(18)·웹훅(56)·워크플로(41)가 같은 구조. Maru 의 이벤트 버스(Phase 2)·알림(M11)을 설계할 때 처음부터 이 셋을 넣는다.
6. **설치·업데이트 고통**: 「페이지 로드 오류 시」 절 반복, 확장 설치 순서, 업데이트 때 사용자 수정 파일 보호(60). → Maru 단일 바이너리·내장 테마·changeset 이 직접 답하는 문제.
7. **AI 로 만든 확장이 많다**(4·33·1·10·60 이 직접 밝힘). G7 의 「AI 친화」는 사람이 AI 로 **확장을 개발**하는 것이고, Maru 의 목표는 에이전트가 **사이트를 운영**하는 것 — 겹치지 않는 차별점이 그대로 유효하다.

## 5. 구현 계획 (승인 대기)

순서 G3 → G1 → G2. 각 단위는 core → storage(필요할 때만, 마이그레이션 + down) → REST → CLI → 테스트 → `scripts/check.ps1` → 커밋. MCP 는 아직 없다.
공개 화면이 바뀌는 G1·G2 는 사용자가 브라우저로 확인한 뒤에 커밋한다.

### G3 — 공개 응답 ETag·304 (S12) · 예상 12만 토큰

- `crates/web`: 공개 라우터(홈·게시판·글·페이지·RSS·사이트맵)에만 미들웨어 한 층. 완성된 응답 본문의 SHA-256 앞 16바이트로 약한 ETag(`W/"…"`)를 달고, `If-None-Match` 가 같으면 본문 없이 304. `Cache-Control: no-cache`(매번 재확인). 관리 화면·`/api`·미리보기·`Set-Cookie` 가 있는 응답은 건드리지 않는다.
- 렌더 비용은 그대로이고 전송량·브라우저 다시 그리기만 줄인다(정직한 효과). 렌더 캐시는 하지 않는다 — 무효화 버그 위험이 효과보다 크다(N100 에서 렌더는 이미 수 ms).
- 스키마 변경 없음, REST·CLI 해당 없음.
- 테스트: `crates/cli/tests/e2e_*.rs` 에 실제 바이너리로 ① 첫 GET 에 ETag ② 같은 ETag 로 304·빈 본문 ③ 글 수정 뒤 200·새 ETag ④ 관리 화면엔 ETag 없음.

### G1 — 제목 앵커 + 자동 목차 (E20) · 예상 25만 토큰

- `core::markdown`: h2~h4 에 `id="h-<슬러그>"` 부여. 슬러그는 한글·영문·숫자만 남기고 공백은 `-`, 영문 소문자, 같은 이름은 `-2`·`-3`, 빈 결과는 `h-<순번>`. 정화 단계 id 허용 규칙(지금은 각주 `fn-N` 만)에 `h-` 접두 규칙을 더한다 — 사용자가 직접 쓴 `id` 는 여전히 버린다(DOM clobbering 방지, 접두로 구분).
- 렌더 결과에 목차 목록(`Vec<TocItem{level, id, text}>`)을 함께 돌려주는 함수 추가. 기존 `render`·`render_with` 시그니처는 유지.
- 설정: `site.toc_min_headings`(기본 3, 0 = 끔) — 설정 서비스에 필드 추가(기본값이 있어 마이그레이션 불필요, `site_settings` 키-값) → REST `PATCH /api/v1/settings` 에 필드, CLI `maru site set --toc-min-headings N` 옵션 추가(검증: 0~20).
- 테마(`builtin/templates/post.html`·`page.html` + `site.css`): 제목이 기준 개수 이상이면 본문 위에 `<nav aria-label="목차">` + `<details open>` 계층 목록. 각 제목 옆에 「이 절 주소」 링크(`#`, 마우스 올리거나 포커스 때만 보임). 고정 헤더일 때 `scroll-margin-top`. 자바스크립트 없음. 모양은 기존 디자인 토큰만 쓴다.
- 테스트: markdown 단위 테스트(한글 제목·중복 제목·빈 제목·사용자 id 제거·코드 블록 안 `#` 무시), insta 스냅숏, e2e(공개 글 HTML 에 목차·앵커, 설정 0 이면 목차 없음, CLI·REST 로 설정 변경).

### G2 — 접기 블록 `:::details` (E21) · 예상 20만 토큰

- 문법: 기존 상자 문법(ADR-0034)에 종류 하나 추가. **첫 문단이 요약(질문)**, 나머지가 내용.
  ```
  :::details
  환불은 언제 되나요?

  결제 후 7일 안에 …
  :::
  ```
  새 노드 종류를 만들지 않으므로 에디터의 기존 상자 노드가 그대로 왕복한다.
- `core::directives`: `details` → `<details class="fold"><summary>첫 문단</summary>…</details>`. 정화 허용 목록에 `details`·`summary` 추가(속성 없음). 첫 문단이 없으면 요약 「자세히」. 상자 안 상자(FAQ 여러 개를 한 상자에)는 기존 중첩 규칙 그대로.
- 에디터: `editor/src/syntax.ts` 의 `BOX_KINDS` 와 `markdown.ts` 의 클래스 매핑에 `details` 한 줄씩, 편집 화면 CSS 에서 첫 문단을 요약처럼 보이게. **도구 막대 단추(main.ts)는 넣지 않는다** — 지금 다른 세션이 main.ts·publish.ts 를 고치는 중이라 겹친다. 단추는 그 세션에 후속으로 넘긴다. `editor.js` 는 다시 묶어 커밋(생성 파일이라 main 과 겹치면 다시 묶어서 해결).
- 공개 CSS: 토큰 색·반경으로 접힘 표시. FAQ 페이지는 이 블록을 여러 개 쓴 페이지로 만든다(별도 FAQ 모듈은 만들지 않음).
- ADR-0041 로 기록(요약 = 첫 문단으로 정한 이유, 대안 `:::details[질문]` 라벨 문법은 에디터 새 노드가 필요해 버림). G1·G3 의 결정은 ADR-0042. (ADR-0040 은 원칙 7 개정이 먼저 썼다.)
- 구현 결과: G3 `b12879a`. G1·G2 는 사용자 브라우저 확인(2026-11-03) 뒤 한 커밋으로. 에디터 「접기 상자 넣기」 단추는 `editor/src/main.ts` 담당 세션의 후속.
- 테스트: directives 단위 테스트(요약·내용 분리, 첫 문단 없음, 중첩, 닫는 줄 없음 → 글자 그대로), 정화 테스트(`<details onclick>` 등 속성 제거), 에디터 왕복은 `editor/test/roundtrip.ts` 에 케이스 추가, e2e 로 공개 HTML 확인.
