## 0. 요약

**결론 세 줄**

1. 현재 SPEC(Phase 4까지 전부 구현했다고 가정)으로 대표 유형 12개 중 **바로 되는 것 3개, 우회하면 되는 것 6개, 막히는 것 3개**다. 막히는 원인은 유형마다 다르지 않고 6가지로 모인다: 고정된 게시판 종류, 순서·계층 없는 페이지, 고정된 홈·URL, 닫힌 블록 목록, 폼 제출 저장소 부재, 첨부 파일 부재.
2. 해법의 중심은 **「정의 가능한 컬렉션 + 공통 필드 타입 + 블록 타입 계약」** 세 가지이고, 모두 SPEC에 이미 씨앗이 있다(`field_schema`, `posts.meta`, `pages.blocks`, `Widget::config_schema`). 새 개념을 들이는 것이 아니라 씨앗을 계약으로 굳히는 작업이다. 대부분 Phase 2~4에 들어간다.
3. **Phase 1에 지금 반영해야 할 것은 2개뿐**이고 둘 다 일정 영향이 거의 없다. (a) 늘어날 열거 값(`boards.kind`, `pages.layout`, `menus.location`, `audit_log.target_type`)에 DB `CHECK` 제약을 걸지 않는다. (b) 공개 URL은 단일 URL 빌더로만 만든다. 컬럼 추가는 하지 않는다(ADR-0010 유지).

## 1. 목표 해석과 경계

### 1.1 「어떤 사이트든」의 범위

「어떤 사이트든」을 문자 그대로 받으면 쇼핑몰, 예약·결제, SaaS 대시보드까지 들어온다. SPEC §0은 쇼핑몰·SMS·본인확인·멀티 테넌트를 범위 밖으로 둔다. 이 제안은 그 경계를 유지하고 목표를 다음처럼 해석한다.

> **콘텐츠 중심 사이트라면 유형을 가리지 않고 Maru 코어로 만든다.** 콘텐츠 중심이란 운영자가 글·페이지·항목을 발행하고, 방문자는 읽고, 필요하면 댓글·문의·신청 같은 짧은 입력을 남기는 사이트다. 돈이 오가는 거래(주문·결제·정산)와 개인 식별(본인확인)은 코어가 맡지 않는다.

SPEC §0 비전 문구 수정안(사용자 결정):

> 에이전트에 한마디 하면, 사용자의 컴퓨터에 **블로그·홈페이지·게시판·커뮤니티부터 문서·매거진·행사·채용 사이트까지, 콘텐츠 중심 사이트라면 무엇이든** 몇 분 만에 멋지게 만들어지는 러스트 CMS 코어. 한국형(게시판 문화, 네이버·카카오, 한글 타이포)은 기본값이자 강점으로 유지한다.

### 1.2 무엇을 바꾸지 않는가

- 원칙 1~7 전부. 특히 원칙 2(최소 코어 + 모듈): 유형별 기능(폼, 이전 도구, 지도)은 모듈로 둔다. 코어에 넣는 것은 **모든 유형이 공유하는 일반화 장치**(컬렉션, 필드 타입, 블록 계약, 라우팅)뿐이다.
- 원칙 4: 컬렉션 정의, 블록 타입, 테마 파일, 라우트, 레시피 적용은 전부 changeset 대상이다(ADR-0001의 「구조·디자인·모듈·설정」 범위 안).
- 원칙 7: 테마 자유도를 넓혀도 외부 디자인 복제 금지는 그대로다. 오히려 §4.6에서 금지 범위를 더 구체적으로 적는다.
- ADR-0010: 컬럼은 읽는 코드가 생기는 Phase에 추가한다. 이 제안은 Phase 1에 컬럼을 하나도 추가하지 않는다.
- 다국어: 사용자 지침(2026-09-28)대로 출시 직전까지 미룬다. 이 제안의 라우팅 설계는 나중에 언어 접두어를 넣을 수 있는지만 막지 않도록 확인한다(§4.4).

## 2. 유형별 판정

**판정 기준**: 현재 SPEC v0.1 설계가 Phase 4까지 구현됐다고 가정한다. Phase 1 실제 범위로는 블로그 하나만 된다(SPEC §15, ADR-0003).

- **된다**: SPEC의 데이터 모델·블록·위젯·프리셋으로 품질 손해 없이 만든다.
- **우회**: 다른 개념을 빌려 쓰면 만들 수 있지만, URL·관리·에이전트 사용성 중 하나 이상이 어색하다.
- **막힌다**: 유형의 핵심 기능을 어떤 조합으로도 표현할 수 없다.

### 2.1 개인 블로그 — 된다 (Phase 1)

- 근거: `blog` 프리셋(§8.6), `boards.kind=blog`(§4), 사이트맵·RSS·메타(§9, §15 Phase 1), Markdown 원본(§16).
- 빈 곳: 태그는 데이터 모델에 없다(ADR-0003). Phase 2로 이미 넘겨져 있다(PHASE1_PLAN §9 「태그 모델도 정한다」). 시리즈(연재 묶음)는 `categories`(§4)로 우회한다.

### 2.2 기술 문서 — 막힌다

- 필요한 것: 문서 트리(장 > 절), 수동 순서, 계층 URL(`/docs/guide/install`), 자동 사이드바, 이전/다음, 문서 안 목차, 코드 하이라이트, 검색.
- 근거:
  - `pages`(§4)는 `slug, title, body_md, layout, blocks, status`뿐이라 부모·순서가 없고, URL은 평면 `/p/{page}`다(ADR-0011).
  - `posts`는 `parent_id, thread_path`가 있지만 댓글·답글 스레드용이고(§4, §2 「답글 정렬 문자열 → parent_id + thread_path」), 목록 정렬은 `published_at` 기준 인덱스뿐이다(§4 인덱스).
  - `menus.location`은 `header/footer` 둘이라(§4) 문서 사이드바 트리를 별도로 둘 곳이 없다. `menu` 위젯(§8.3, Phase 2)으로 사이드바 영역에 붙이는 우회는 가능하지만 이전/다음과 계층 URL은 여전히 없다.
  - 코드 하이라이트는 SPEC에 언급이 없다.
- 우회 한계: 10쪽 안팎의 소규모 문서는 `blog` 게시판 + 분류 + 수동 메뉴로 흉내 낼 수 있으나 「문서 사이트」라고 부르기 어렵다.

### 2.3 회사 소개 — 우회 (Phase 2)

- 근거: 블록 기반 페이지(§4 `pages.blocks`, §15 Phase 2), 섹션 블록 히어로·기능 그리드·벤토·후기·CTA·연락처 폼(§8.5), 공지 게시판(§4 kind `notice`).
- 걸림:
  - 홈은 템플릿 고정이다(ADR-0003 「홈 최신글은 템플릿에 고정」, ADR-0011 `/`). Phase 2부터 `page_scope: "home"` 위젯 배치(§8.3)로 홈을 꾸밀 수 있지만, 홈을 **블록 페이지 하나로 지정**하는 설정은 없다.
  - 연혁·조직도 블록은 `org` 프리셋 설명(§8.6)에만 나오고 블록 카탈로그(§8.5)에는 없다. **SPEC 내부 불일치**다.
  - 연락처 폼 블록(§8.5)은 있으나 제출을 저장할 테이블이 없다. §5.3은 「외부 사용자 콘텐츠(댓글, 문의)」를 언급하지만 문의 모델이 §4에 없다.
  - 하위 페이지(`/about/history`)가 평면 슬러그라 계층 URL이 안 된다.

### 2.4 랜딩 페이지 — 우회 (Phase 2)

- 근거: 블록 페이지(§4), `pages.layout`(§4)으로 헤더·푸터를 줄인 레이아웃을 줄 수 있다.
- 걸림: 홈을 그 페이지로 바꿀 수 없다(위와 같음). 사전 신청·뉴스레터 구독 같은 리드 수집은 저장소가 없다. 단일 페이지 사이트는 홈 위젯 배치로 흉내 낼 수 있다.

### 2.5 포트폴리오 — 우회 (Phase 4)

- 근거: `portfolio` 프리셋(§8.6, Phase 4), `gallery` kind(§4), 게시판별 `field_schema` + `posts.meta`(§2, §4).
- 걸림:
  - 작업물은 클라이언트, 연도, 역할, 사용 기술, 외부 링크 같은 필드가 핵심이다. `field_schema`는 「JSON Schema」라고만 정의돼 있고(§2), **템플릿이 meta 필드를 어떻게 받아 표시하는지, 날짜·이미지·링크를 어떤 타입으로 다루는지 렌더 계약이 없다.**
  - 정렬은 발행일뿐이라 「연도순」, 「대표작 먼저」를 못 한다.
  - 대표 이미지(커버)가 `posts` 컬럼에 없다. meta로 넣어야 하는데 위 렌더 계약이 없다.

### 2.6 소상공인 가게 — 된다 (Phase 4)

- 근거: `cafe` 프리셋(§8.6), 영업시간·오시는 길 블록(§8.5), `map` 모듈(§9), `kakao` 채널 버튼(§9), 공지·갤러리 게시판.
- 빈 곳: §8.6은 「메뉴」 블록을 말하지만 §8.5에 가격표(메뉴판) 블록이 없다(불일치). 영업시간·주소·전화번호가 블록마다 따로 들어가면 푸터·지도·검색 메타와 값이 어긋난다. 「단일 항목 데이터」를 둘 곳이 없다(§4.7에서 다룸).

### 2.7 기관·단체 — 우회 (Phase 4)

- 근거: `org` 프리셋(§8.6): 공지·자료실·FAQ, 소개·연혁·조직도.
- 걸림:
  - **자료실 = 첨부 파일 게시판**이다. `media`(§4)는 있으나 글과 미디어를 잇는 관계가 없고, 업로드 규칙(§13 「MIME 스니핑 + 확장자 화이트리스트, 이미지 재인코딩」)은 이미지 중심이라 PDF·HWP·HWPX 같은 문서 파일 허용 범위가 정해져 있지 않다. kind 목록(§4)에 자료실이 없다.
  - 연혁·조직도 블록 미정의(위와 같음).

### 2.8 커뮤니티 — 된다 (Phase 4)

- 근거: `community` 프리셋(§8.6), 회원·역할·댓글 승인 큐·비밀글·공지·분류(§15 Phase 4), `social_login`(§9), 게시판 정책(§5.2), 포인트·추천·스크랩·쪽지 모듈(§9, Phase 4 이후).
- SPEC이 가장 깊게 설계한 유형이다. 이 제안으로 바뀌는 것은 없다.

### 2.9 매거진·뉴스 — 우회 (Phase 4)

- 근거: 섹션별 게시판(§4), 분류(§4 `categories`), `latest_posts` 위젯(§8.3).
- 걸림:
  - 첫 화면은 여러 섹션을 가로지르는 편집(헤드라인, 편집자 추천)이다. `latest_posts`의 설정 예는 `board: "notice"` 하나다(§8.3). 게시판 횡단 목록이나 「추천」 표시 기준이 없다.
  - 대표 이미지·부제·기자(저자) 프로필 페이지가 없다. `members`(§4)는 `email, display_name, password_hash, status`뿐이다.
  - 예약 발행: `published_at`은 있지만 미래 시각을 발행 트리거로 쓰는 규칙이 없다. 외부 cron + `maru post publish`로 우회할 수 있다.
  - 연관 기사는 태그(Phase 2) 이후 가능.

### 2.10 이벤트·행사 — 막힌다

- 필요한 것: 행사 항목(시작·종료 일시, 장소, 정원, 신청 링크 또는 신청 폼), 「다가오는 행사 / 지난 행사」 목록(**발행일이 아닌 행사일 기준**), 세션 시간표, 참가 신청.
- 근거: 목록 조회는 `posts(board_id, status, published_at)` 인덱스 기준(§4)이고 meta 필드로 정렬·필터하는 조회가 SPEC에 없다. 신청 저장소가 없다(2.3과 같음).
- 우회 한계: 행사 하나짜리 마이크로 사이트는 랜딩 페이지 우회(2.4)로 된다. 여러 행사를 운영하는 사이트는 안 된다.

### 2.11 강의·교육 — 막힌다 (강좌 소개 사이트는 우회)

- 필요한 것: 강좌 > 차시 관계, 차시 순서, 수강생 전용 공개, 진도.
- 근거: 글 사이 관계(참조) 필드가 없다(§4). 순서는 발행일뿐. 수강생 전용 공개는 게시판 정책 `read: "member"`(§5.2)로 게시판 단위 우회가 된다.
- 경계: 수강료 결제는 SPEC §0 범위 밖(쇼핑몰)이고 이 제안도 유지한다. 진도 관리는 학습 관리 시스템(LMS) 영역이라 코어가 아닌 모듈 후보로만 남긴다. 「강좌 소개 + 회원 전용 강의 노트」 수준은 컬렉션(§4.1)이 생기면 된다.

### 2.12 채용 — 우회 (Phase 4)

- 근거: 게시판 + `field_schema`(직군, 고용 형태, 근무지, 마감일).
- 걸림: 마감일 기준 정렬·자동 「마감」 표시는 meta 조회·렌더 계약이 없어 어렵다. 지원서 접수는 개인정보와 파일(이력서)을 받는 폼이라 저장소도, 첨부도 없다. 외부 지원 링크로 우회한다.

## 4. 확장 설계 제안

각 제안은 **문제 → 제안 → 참고한 다른 CMS → Phase → Phase 1 영향 → 비용 → 대안** 순서다. 비용은 경험 기반 추정이며 측정값이 아니다(단위: 작업일, 1인 기준. SPEC §15의 Phase 길이와 비교용).

### 4.1 P1 — 정의 가능한 컬렉션 (G1, G2 일부)

**문제.** `boards.kind`가 `blog, notice, gallery, free, qna, faq` 6개로 닫혀 있다(§4). 그누보드의 여분 필드를 개선한 `field_schema`(§2)는 좋은 씨앗이지만, 필드가 무슨 타입이고 템플릿이 어떻게 받고 무엇으로 정렬·필터하는지가 없다.

**제안.**

1. **개념**: 게시판을 일반화한 「컬렉션」. 저장은 지금처럼 `boards` 테이블과 단일 `posts` 테이블(§2의 결정 유지)을 쓴다. 사용자·관리 화면 용어는 게시판형이면 「게시판」, 아니면 「컬렉션」으로 보여 준다. 테이블 이름은 바꾸지 않는다(SPEC·계획 문서 전반의 개명 비용 대비 이득이 없다).
2. **`kind`의 의미 변경**: 닫힌 타입이 아니라 **출발점 묶음**(기본 기능 플래그 + 기본 필드 + 기본 뷰). 내장 kind는 `blog, notice, gallery, free, qna, faq`에 `custom`을 더한다. 이후 `docs`, `event`, `job`, `project` 같은 kind는 코어 코드가 아니라 **레시피(§4.5)가 만드는 컬렉션 정의**로 제공한다.
3. **컬렉션 정의** (changeset op `collection.define` / `collection.update`):

```json
{
  "slug": "events",
  "name": "행사",
  "kind": "custom",
  "features": {
    "comments": false,
    "categories": true,
    "order": { "by": "meta.starts_at", "dir": "asc" },
    "feed": true,
    "sitemap": true
  },
  "fields": [
    { "key": "starts_at", "type": "datetime", "label": "시작", "required": true, "index": true },
    { "key": "ends_at",   "type": "datetime", "label": "종료" },
    { "key": "venue",     "type": "text",     "label": "장소", "max": 80 },
    { "key": "cover",     "type": "media",    "label": "대표 이미지", "accept": ["image"] },
    { "key": "apply_url", "type": "url",      "label": "신청 링크" }
  ],
  "views": { "list": "event_list", "item": "event" },
  "permalink": "/events/{slug}"
}
```

4. **공통 필드 타입** (컬렉션·블록·폼·모듈 설정이 모두 같은 타입 체계를 쓴다. ADR-0018):

| 타입 | 저장(JSON) | 렌더 시 템플릿이 받는 값 | 메모 |
|---|---|---|---|
| `text` / `textarea` | 문자열 | 자동 이스케이프되는 문자열 | `max` |
| `markdown` | Markdown 문자열 | **정화된 HTML 타입**(U7의 정화 전용 타입 재사용) | `|safe`는 이 타입만 |
| `number` | 숫자 | 숫자 | `min`, `max`, `step` |
| `boolean` | 참/거짓 | 참/거짓 | |
| `date` / `datetime` | RFC3339 | 날짜 객체(한국어 표기 필터 제공) | 타임존은 `site_settings` |
| `select` / `multiselect` | 문자열 / 배열 | 값과 표시명 | `options` |
| `url` / `email` / `phone` | 문자열 | 검증된 문자열 | `url`은 스킴 허용 목록(U7 규칙) |
| `media` | 미디어 ULID | 경로·크기·alt·variants | `accept` |
| `ref` | 글 ULID 또는 배열 | 대상 글 요약(제목·URL) | `collection`, `many`. 강좌-차시, 저자 연결 |
| `group` / `list` | 객체 / 객체 배열 | 같은 구조 | 반복 필드(일정표, 가격표) |

   - **완전한 JSON Schema 대신 부분집합**을 쓰는 이유: 렌더러가 타입 의미(날짜 표기, 미디어 URL 해석, Markdown 정화)를 알아야 하고, 에이전트가 채우기 쉬워야 한다. 필드 정의에서 JSON Schema를 **생성**해 MCP 툴 입력 스키마(§11)와 설정 폼에 쓴다. 방향이 「필드 정의 → JSON Schema」이므로 schemars 원칙(CLAUDE.md 스택 표)과 충돌하지 않는다.
   - 저장 시 core가 검증한다(권한 검사와 같은 위치, 원칙 1). 정의에 없는 키는 거부하고, 정의가 바뀌어 남은 옛 키는 보존하되 렌더하지 않는다.
5. **조회 계약**: `list_posts { collection, filter: [{ field, op, value }], sort, limit, cursor }`. `op`은 `eq, in, gte, lte, exists`만. 필드는 `index: true`인 것만 필터·정렬에 쓸 수 있다.
   - 구현: SQLite JSON 함수 `json_extract(meta, '$.key')`에 컬렉션별 **부분 식 인덱스**를 changeset 적용 시 만든다. 이는 런타임 DDL이고, PHASE1_PLAN §10이 적은 sqlx 0.9 규칙(「`query*()`는 정적 문자열이나 `AssertSqlSafe`만 허용」)상 `AssertSqlSafe`가 필요하다. 필드 키는 `^[a-z][a-z0-9_]{0,31}$`로만 허용하고 그 외는 SQL에 닿기 전에 거부한다. 이 부분은 보안 검토 대상으로 표시한다.
   - 공개 조회 함수 통일(PHASE1_PLAN §4.6)을 유지한다. 컬렉션 조회도 같은 공개 범위 함수를 지난다.
6. **뷰 템플릿 선택 순서** (WordPress 템플릿 계층과 같은 발상, 아래 참고):
   `collections/{slug}/list.html` → `kinds/{kind}/list.html` → `board_list.html`(Phase 1 이름 그대로) / 상세도 같은 방식으로 `post.html`까지 내려간다. Phase 1 템플릿 이름이 마지막 대체가 되므로 Phase 1 테마는 깨지지 않는다.
7. **관계와 저자**: `ref` 필드로 강좌-차시, 기사-기자를 잇는다. 역참조(「이 강좌의 차시들」)는 `json_each`로 조회한다. 기자 프로필은 `members`를 늘리지 않고 「저자」 컬렉션 + `ref`로 푼다(회원이 아닌 필자도 있다).

**참고한 다른 CMS** (2026-11-02 공식 문서 확인, 출처는 부록 B)

- Strapi는 콘텐츠 타입을 다루는 엔트리 수에 따라 collection type과 single type으로 나누고, `schema.json`의 `attributes`에 `type`(string, media, relation, component, dynamiczone 등)과 검증(`required`, `min`, `max`…)을 둔다. Maru의 필드 타입 표는 이 구조를 축소한 형태다.
- Payload는 collection마다 `slug`와 `fields`를 정의하면 Local·REST·GraphQL API를 자동 생성한다. Maru는 같은 발상으로 컬렉션 정의에서 REST·CLI·MCP 입력 스키마를 함께 만든다(원칙 1·3).
- WordPress 블록 테마는 단일 항목 템플릿을 `single-{post_type}-{post_name}.html` → `single-{post_type}.html` → `single.html` → `singular.html` → `index.html` 순으로 찾는다. 6항의 선택 순서가 같은 구조다.

**Phase.** Phase 2. SPEC §15 Phase 2에 「블록 기반 페이지」가 이미 있고, 블록과 컬렉션이 같은 필드 타입을 공유하므로 함께 들어가야 중복 구현이 없다.

**Phase 1 영향.** 컬럼 추가 없음(ADR-0010 유지: `field_schema`, `meta`, `view_template`은 Phase 2 마이그레이션에서 읽는 코드와 함께). **단 하나, `boards.kind`에 DB CHECK를 걸지 않는다**(§6, ADR-0016). Phase 1에서 `CHECK(kind IN (...))`를 걸면, SQLite는 ALTER TABLE로 CHECK를 바꿀 수 없어 테이블 재작성 12단계 절차가 필요하다(부록 B, SQLite 공식 문서).

**비용.** 필드 타입·검증·JSON Schema 생성 4~5일, 조회 계약·식 인덱스 3~4일, 뷰 선택 순서·템플릿 컨텍스트 2일, REST·CLI·MCP 노출 3일. 합계 약 2.5~3주. Phase 2 예정(2~3주)이 사실상 두 배가 된다(§5에서 분할안).

**대안.**

- (A) kind만 몇 개 더 추가(`docs`, `event`, `job`): 싸지만 유형이 늘 때마다 코어 수정이 필요하다. 「어떤 사이트든」 목표와 맞지 않는다.
- (B) 컬렉션마다 실제 테이블 생성: 정렬·인덱스가 자연스럽지만 그누보드에서 버린 「게시판별 테이블」(§2)로 되돌아가고, 마이그레이션·백업·changeset 역연산이 복잡해진다.
- (C) 완전한 JSON Schema 허용: 표현력은 크지만 렌더 계약을 정의할 수 없다.

### 4.2 P2 — 페이지 계층·순서와 문서 레이아웃 (G2)

**제안.**

- `pages`에 `parent_id`, `sort_order`를 추가하고 URL을 경로형(`/about/history`)으로 만든다(라우팅은 §4.4). 같은 부모 안에서 슬러그 유일.
- `layout: "docs"`: 부모 페이지 아래 트리로 사이드바·이전/다음·문서 안 목차(제목에서 생성)를 자동 렌더한다. 기술 문서는 「페이지 트리 + docs 레이아웃」으로 푼다. 문서는 시간순·댓글이 필요 없어 글보다 페이지에 가깝다.
- 문서 버전(v1/v2 병행)은 이번 범위에서 뺀다. 필요해지면 트리 루트를 버전별로 두는 방식으로 시작한다.
- 코드 하이라이트: 서버 측 하이라이트 크레이트는 바이너리 크기 목표(§14 30MB)에 영향이 있을 수 있어 측정 후 결정한다. 측정 전 기본값은 언어 라벨 + 고정폭 + 토큰 색만.

**Phase.** Phase 2(블록 페이지와 같은 마이그레이션). 문서 레이아웃은 Phase 4 테마 작업과 함께.

**Phase 1 영향.** 없음. `pages.layout`에 CHECK를 걸지 않는 것만 ADR-0016에 포함.

**비용.** 트리·검증(순환 금지)·경로 URL 3일, docs 레이아웃 3~4일.

**대안.** 글(`posts`)의 `parent_id`를 문서 계층에도 쓰는 안. 댓글 스레드 의미와 섞여 조회·권한 규칙이 복잡해진다. 강좌-차시처럼 글 사이 관계가 필요한 경우는 `ref` 필드(P1)로 충분하다.

### 4.3 P3 — 블록 타입 계약과 위젯 통합 (G4)

**문제.** §8.5는 블록 이름 목록뿐이다. `pages.blocks`(JSON)의 모양, 블록이 받는 데이터, 렌더 방법, 버전 변경 시 처리, 모듈이 블록을 추가하는 방법이 없다. 한편 위젯(§7.2 `Widget` 트레이트)은 `config_schema`와 `render`를 가진, 사실상 같은 물건이다.

**제안.**

1. **블록 타입 = 위젯 타입.** 렌더 단위를 하나로 통일한다. 차이는 놓이는 곳뿐이다.
   - 블록 인스턴스: 페이지(또는 홈)의 `blocks` 배열 안에 콘텐츠로 저장.
   - 위젯 인스턴스: `widget_instances`(§4)에 영역(region)·`page_scope`와 함께 저장. `type`이 블록 타입 id를 가리킨다.
   - 코어 트레이트는 §7.2의 `Widget`을 이름만 바꿔 `BlockType`으로 한다(`id`, `name`, `config_schema` → 필드 정의, `render`). 모듈의 `widgets()`는 `block_types()`가 된다. 모듈이 지도 블록을 주면 페이지에도 영역에도 놓인다.
2. **블록 타입 정의 파일** (테마 또는 모듈이 제공, `themes/<id>/blocks/<block>/`):

```toml
# block.toml
[block]
id = "core/timeline"          # 네임스페이스/이름
name = "연혁"
version = 1
contexts = ["page", "region:main"]

[[fields]]                     # P1의 공통 필드 타입
key = "items"
type = "list"
label = "연혁 항목"
fields = [
  { key = "year", type = "text", label = "연도", required = true },
  { key = "text", type = "markdown", label = "내용" },
]

[[variants]]                   # 토큰 안에서 고르는 모양 선택지
id = "vertical"
name = "세로"

[example]                      # 미리보기·에이전트 예시 데이터
items = [{ year = "2024", text = "설립" }]
```

   템플릿은 같은 폴더의 `block.html`(minijinja).
3. **인스턴스 데이터 모델**:

```json
{ "id": "01J…", "type": "core/timeline", "v": 1, "variant": "vertical",
  "spacing": "md", "tone": "surface",
  "data": { "items": [ { "year": "2024", "text": "설립" } ] } }
```

   - `id`는 changeset diff와 미리보기에서 블록 하나를 가리키는 안정 키.
   - `variant`, `spacing`, `tone`은 **토큰 위의 선택지**일 뿐 임의 CSS 값이 아니다(§8.2 「에이전트는 CSS를 직접 쓰지 않는다」 유지).
   - 중첩은 1단계(열 나누기 같은 컨테이너 블록 안에 블록)까지만.
4. **렌더 계약**:
   - 템플릿은 검증을 통과한 `data`, `block`(id·variant 등), `site`, 그리고 **블록 정의가 선언한 데이터 질의 결과**만 받는다. 템플릿은 DB에 직접 닿지 않는다.
   - 데이터 질의는 선언형이다. 예: `query = { collection = "notice", limit = 5 }` → P1의 공개 조회 함수 결과. 게시판 횡단(`collections = ["news", "column"]`, `filter = [{ field = "meta.featured", op = "eq", value = true }]`)도 같은 계약으로 표현해 매거진 첫 화면(2.9)을 푼다.
   - 자동 이스케이프 유지. `|safe`는 `markdown` 타입(정화된 값)에만. PHASE1_PLAN §7의 「내장 테마 `|safe` 검사 스크립트」를 사용자 블록에도 돌린다.
   - 블록 렌더 실패는 그 블록만 빈 자리로 두고 페이지는 렌더한다(§7.3의 「비활성 모듈 위젯은 조용히 제외」와 같은 규칙). 관리 화면과 미리보기에는 경고를 띄운다.
5. **버전**: 블록 정의의 `version`이 오르면 정의에 `[migrate]`로 기본값 채우기·키 이름 바꾸기 같은 선언형 변환만 허용한다. 변환이 불가능한 인스턴스는 옛 데이터를 보존하고 경고한다.
6. **카탈로그 보강** (§8.5와 §8.6의 불일치 해소): 연혁, 조직도, 가격표(메뉴판), 일정표, 팀 소개, 통계 숫자, 로고 모음, 파일 목록(자료실 연동), 게시판 횡단 목록. 모두 P1 필드 타입으로 표현된다.
7. **블록을 쓸 수 있는 곳**: Phase 2는 페이지와 홈. 글 본문은 Markdown 원본 유지(§16 결정). 필드 타입 `blocks`(컬렉션 항목 안의 블록 영역)는 행사 상세 같은 수요가 확인되면 Phase 4 이후에 검토한다.

**참고한 다른 CMS** (부록 B)

- WordPress `block.json`은 `namespace/block-name` 이름, `attributes`, `supports`, 그리고 서버 렌더용 `render`(PHP 파일, `$attributes`·`$content`·`$block`을 받음)를 한 메타데이터 파일에 둔다. Maru의 `block.toml` + `block.html`은 같은 분리를 minijinja로 옮긴 것이다. 다만 WordPress 속성은 저장된 마크업에서 값을 읽는 `source`/`selector` 방식을 쓰는 반면, Maru는 JSON 데이터를 원본으로 둔다(Markdown 원본 원칙과 같은 방향, 에이전트가 HTML을 파싱할 필요가 없다).
- Payload의 Blocks 필드는 블록마다 `slug`와 `fields`를 두고, 저장 시 각 항목에 `blockType`으로 slug를 남긴다. 블록 정의를 최상위에 한 번 두고 slug로 재사용하는 block references도 있다. Maru 인스턴스의 `type` 키와 테마·모듈 단위 블록 등록이 같은 구조다.
- Strapi의 dynamic zone은 허용할 component 목록을 받아 섞어 쓰는 영역이다. Maru 블록의 `contexts`와 영역별 허용 목록이 같은 역할이다.

**Phase.** Phase 2(위젯·블록 페이지가 원래 Phase 2).

**Phase 1 영향.** 없음. `pages.blocks`는 ADR-0010대로 Phase 2에서 추가한다.

**비용.** 통합 트레이트·레지스트리 2일, 정의 파일 로더·검증 3일, 렌더 계약·선언형 질의 3일, 버전 변환 2일, 카탈로그 보강은 Phase 4 테마 작업에 포함. 위젯과 블록을 따로 만들 때보다 Phase 2 전체는 오히려 줄어든다(렌더 경로가 하나).

**대안.** 위젯과 블록을 별도 시스템으로 유지(SPEC 현재 형태). 모듈이 기능 하나를 두 번 등록해야 하고, 에이전트에게 「위젯인가 블록인가」 판단을 떠넘긴다.

### 4.4 P4 — 라우팅: 홈 교체, 퍼머링크 패턴, 리다이렉트 (G3)

**제안.**

1. **홈 설정** `site_settings.home` = `{ "type": "latest" }`(기본, Phase 1 동작) | `{ "type": "page", "page": "<id>" }` | `{ "type": "collection", "collection": "<slug>" }`. `site_settings`는 키-값 JSON(§4)이라 **스키마 변경이 필요 없다.**
2. **컬렉션 퍼머링크 패턴**: `permalink: "/blog/{slug}"`, `"/news/{yyyy}/{mm}/{slug}"`, 목록 경로 `"/blog"`. 변수는 `{slug}`, `{yyyy}`, `{mm}`, `{dd}`, `{category}`만. 기본값은 ADR-0011의 `/b/{board}/{post}` 그대로.
3. **페이지 경로**: P2 트리에서 `/about/history`. 기본값은 ADR-0011의 `/p/{page}`, 사이트가 「접두어 없는 페이지 경로」를 켜면 `/about/history`.
4. **리다이렉트 테이블** `redirects(from_path, to_target, code, source)`: 슬러그 변경 시 자동 301 생성(ADR-0011의 「Phase 1은 404」를 Phase 2에서 해소), 이전(§4.6)의 옛 URL 보존, 수동 등록. **Phase 1의 슬러그 변경 이력은 ADR-0001에 따라 `audit_log.diff`에 변경 전 값이 남으므로 Phase 2에서 리다이렉트를 소급 생성할 수 있다.** Phase 1에 따로 할 일은 없다.
5. **예약 경로**: `/admin`, `/api`, `/__preview`, `/mcp`, `/media`, `/assets`, `/sitemap.xml`, `/rss.xml`, `/robots.txt`, 그리고 `/.well-known/`. 사용자 경로·패턴이 이와 겹치거나 서로 겹치면 changeset 생성 단계에서 `CONFLICT`(종료 코드 4)로 거부하고 `next`를 준다.
6. **구현 방향**: 예약 경로는 axum 정적 라우트, 나머지는 하나의 폴백 핸들러가 라우트 표로 해석한다. PHASE1_PLAN §4.4는 「CLI로 바꾼 것이 실행 중 서버에 바로 보여야 해서 프로세스 안에 캐시하지 않는다」고 정했다. 라우트 표도 같은 규칙을 따른다. 요청마다 작은 표를 읽거나, `site_settings`의 구조 버전 카운터만 읽고 바뀌었을 때 다시 읽는다(성능 문제가 측정되면).
7. **사용자 정의 라우트 표**(Ghost의 `routes` 같은 「임의 경로 → 페이지/목록」)는 위 1~4로 대부분의 수요가 풀리므로 Phase 3 이후로 미룬다.
8. **다국어**: 설계하지 않는다(사용자 지침). 확인할 것은 하나다. 퍼머링크 패턴과 예약 경로 규칙이 나중에 `/{lang}/` 접두어를 앞에 붙이는 것을 막지 않는가. 위 설계는 막지 않는다.

**참고한 다른 CMS** (부록 B). Ghost는 `routes.yaml`에 `routes`(임의 URL → 템플릿), `collections`(필터로 글 묶음, `permalink`·`template` 지정), `taxonomies`를 둔다. 글은 한 collection에만 속하고, 홈을 비우려면 `/: home` 라우트를 두고 메인 collection을 `/blog/`로 옮긴다. 「글이 속한 곳이 URL을 정한다」는 점이 Maru 「컬렉션 퍼머링크」와 같고, 「홈을 다른 것으로 바꾼다」는 Maru 1항과 같다. Maru는 파일 편집 대신 changeset op로 바꾼다.

**Phase.** 홈 설정·퍼머링크·리다이렉트·예약 경로는 Phase 2(컬렉션과 함께). 라우트 변경의 changeset 미리보기는 Phase 3. 사용자 정의 라우트 표는 Phase 3 이후.

**Phase 1 영향.** **단일 URL 빌더**(§6, ADR-0017). 템플릿·사이트맵·RSS·`next` 힌트·관리 화면이 `"/b/" ~ board.slug` 같은 문자열 조합을 하면, Phase 2에 퍼머링크를 바꿀 때 모든 템플릿과 사용자 테마(Phase 1부터 복사 가능, U10)를 고쳐야 한다. 지금 `url_for(target)` 한 곳으로 모으면 비용이 거의 없다.

**비용.** 홈 설정 1일, 퍼머링크·경로 해석 3~4일, 리다이렉트·소급 생성 2일, 충돌 검증 1일.

**대안.** ADR-0011 고정 URL 유지. 이전(§4.6) 시 기존 URL을 보존할 수 없어 검색 노출을 잃는다. 한국형 승부처인 네이버 검색 노출(§0)과 충돌한다.

### 4.5 P5 — 프리셋을 「조합 가능한 레시피」로 (G9)

**문제.** 프리셋은 「테마 + 토큰 + 게시판 + 페이지 + 메뉴 + 위젯 + 모듈」 고정 세트다(§8.6). 「카페인데 블로그도, 예약 문의도」는 프리셋 조합이 아니라 손작업이 된다.

**제안.**

1. **레시피** = 이름 있는 **매개변수화된 changeset op 묶음**. op 어휘는 changeset(§6)과 같다. 레시피를 적용하면 changeset 하나가 생기고, 미리보기 → 승인 → 적용 → 롤백 흐름(원칙 4)을 그대로 탄다.

```toml
[recipe]
id = "contact-form"
name = "문의 받기"
version = 1
requires = ["module:forms"]

[[params]]                      # P1 필드 타입
key = "page_slug"
type = "text"
default = "contact"

[[ops]]
op = "form.ensure"
slug = "contact"
fields = ["name", "email", "message"]

[[ops]]
op = "page.ensure"
slug = "{{ params.page_slug }}"
blocks = [{ type = "core/contact_form", data = { form = "contact" } }]

[[ops]]
op = "menu.ensure_item"
location = "header"
label = "문의"
target = { page = "{{ params.page_slug }}" }
```

2. **멱등**: op은 `create`가 아니라 `ensure`(없으면 만들고, 있으면 정의와 같은지 확인)를 기본으로 한다. 원칙 3의 「여러 번 실행해도 안전」과 SPEC §10.1의 `--if-not-exists`를 레시피 수준으로 끌어올린 것이다. 다르면 diff를 보여 주고 덮어쓸지 묻는다(`--yes`면 정책대로).
3. **프리셋** = 레시피 목록 + 테마 + 토큰. `cafe = ["site-profile", "notice-board", "gallery", "menu-price", "location-hours", "kakao-channel"]`. 기존 5개 프리셋(§8.6)은 레시피 조합으로 다시 정의한다.
4. **인터페이스**: `maru recipe list/show/apply --param k=v --json`, MCP `list_recipes`, `apply_recipe`(스코프 `structure`·`design`, changeset 필수). 에이전트는 사용자 요청을 레시피 목록으로 번역한다. 「카페 + 블로그 + 문의」 → `apply_recipe` 세 번이 changeset 하나에 쌓인다.
5. **유형 매트릭스를 회귀 시험으로**: §2의 12개 유형을 각각 레시피 조합으로 정의하고, Phase 4 완료 기준에서 「에이전트 한마디로 구성 → 미리보기 렌더 → 승인 → 공개 페이지 HTTP 확인」을 유형별로 돌린다.

**Phase.** 레시피 형식과 `apply_recipe`는 Phase 3(changeset op 어휘가 그때 확정). 프리셋 재정의와 유형 매트릭스는 Phase 4.

**Phase 1 영향.** 필수 변경 없음. 권장(선택): U10의 `blog` 프리셋 TOML을 처음부터 `[[ops]]` 목록 모양으로 쓰고, 적용은 서비스 호출 순서로 한다. 서비스 호출로 적용하는 것은 `WriteTx` 감사 규칙(ADR-0007) 때문에 이미 필요하므로, 차이는 파일 모양뿐이다.

**비용.** 레시피 로더·템플릿 치환·`ensure` 의미 4~5일(Phase 3), 기존 프리셋 재정의 3일(Phase 4).

**대안.** 프리셋을 계속 늘림(`cafe-with-blog` 등). 조합 폭발. 또는 에이전트가 매번 저수준 op을 직접 조립: 가능하지만 결과 품질이 에이전트마다 흔들리고, 검증된 구성을 재사용할 수 없다.

### 4.6 P6 — 테마 자유도의 경계 (G8)

**문제.** §8.2는 「에이전트는 CSS를 직접 쓰지 않고 토큰과 블록 조합으로」라고 하지만, §3.3·§8.1은 사용자 테마 폴더에 템플릿을 복사·수정하는 길을 이미 열어 두었고, Phase 1 U10이 「사용자 테마 우선 로더」를 만든다. 어디까지가 허용인지, 그 변경이 changeset 안에 있는지가 정해져 있지 않다. changeset ops(§6)는 DB 연산 중심이라 **테마 파일 수정은 현재 changeset 밖**이다.

**제안: 자유도 5단계**

| 단계 | 바꾸는 것 | 누가 | changeset | Phase |
|---|---|---|---|---|
| L0 토큰 | `tokens.json` 값 | 에이전트 기본 | 예 | 3(Phase 1은 직접 적용) |
| L1 블록 선택지 | `variant`, `spacing`, `tone` | 에이전트 기본 | 예 | 2~3 |
| L2 템플릿 덮어쓰기·사용자 블록 | `templates/*.html`, `blocks/*/` | 에이전트(`design` 스코프) | 예, 파일 op | 3 |
| L3 사용자 CSS | `assets/custom.css` 하나 | 에이전트(`design`) | 예 | 3 |
| L4 사용자 JS | `assets/*.js` | **사람이 명시적으로 허용한 경우만** | 예 + 별도 승인 표시 | 4 이후, 사용자 결정 |

- **템플릿 컨텍스트 계약**: 템플릿마다 받는 변수 목록을 문서화하고 `theme.toml`에 `template_api = 1`을 둔다. 코어가 계약을 깨는 변경을 하면 번호를 올리고, 옛 번호 테마는 경고와 함께 내장 템플릿으로 대체한다(PHASE1_PLAN §4.6 「사용자 테마 삭제 → 내장 테마로 복귀」와 같은 경로).
- **관리 화면(`/admin`)과 미리보기 크롬은 덮어쓸 수 없다.** 사용자 테마는 공개 사이트만.
- **CSS·JS 안전선**: 사용자 CSS는 외부 `@import`·외부 `url()`을 거부하고, CSP `style-src 'self'`·`img-src 'self'`(PHASE1_PLAN §7 응답 헤더)로 외부 유출 경로를 막는다. JS는 CSP `script-src 'self'`의 테마 자산만. 사용자 입력이 템플릿·CSS로 흘러가지 않는다(토큰 형식 검증과 같은 원칙, PHASE1_PLAN §2 「디자인 토큰 CSS」).

**changeset 안에서 테마 파일 다루기**

- op: `theme.write_file { theme, path, content, base_hash }`, `theme.delete_file { theme, path, base_hash }`, `block_type.define`.
- 적용 시 이전 내용 전체를 changeset에 저장해 revert에 쓴다(§6 「역연산을 함께 저장」).
- `base_hash`는 사람이 같은 파일을 손으로 고친 경우를 잡는다. 해시가 다르면 `CONFLICT`.
- 미리보기: 템플릿 로더를 **겹 구조**로 둔다. `changeset 오버레이 → 사용자 테마 폴더 → 내장 테마`. U10의 「사용자 테마 우선 로더」를 처음부터 「소스 목록을 순서대로 찾는 로더」로 만들면 Phase 3에서 오버레이 한 겹만 추가하면 된다(Phase 1 권장 사항, §6).
- 저장 위치는 디스크 유지(SPEC §3.3)를 추천한다. 에이전시·개발자 타깃은 테마를 git으로 관리하고 편집기로 연다. 대안은 DB 저장(백업 원자성, 오버레이 단순). 사용자 결정 Q3.

**원칙 7 안에서 허용하는 방법**

- 허용: 토큰·블록·사용자 템플릿으로 **새로 설계**한 결과, 사용자가 권리를 가진 자산(직접 찍은 사진, 자기 로고, 라이선스 확인된 폰트), MIT·CC0 등 재배포 가능 자산(`THIRD_PARTY.md` 기록, §8.7).
- 금지: 다른 사이트의 HTML·CSS·JS·이미지·일러스트를 가져와 테마에 넣는 것, 특정 사이트의 고유한 화면 구성을 재현하는 것(§8.7).
- 「OO 사이트처럼 해 줘」 요청 처리: 에이전트는 그 사이트를 가져오지 않고, 패턴 서술(예: 「큰 타이포 히어로 + 3열 벤토 + 넓은 여백」)로 바꿔 블록·토큰 조합을 제안한다. `AGENTS.md`와 MCP 툴 설명(§11 「쓰지 말아야 할 때」)에 적는다.
- 기술적 장치: `theme.toml`에 `[[assets]] path, origin("original"|"user-owned"|"third-party"), license`를 두고, 자산이 이 목록에 없으면 changeset 검증이 실패한다. changeset 미리보기 화면에 자산 출처 목록을 보여 승인자가 본다. **기술로 복제를 완전히 막을 수는 없다**(에이전트가 남의 CSS를 「직접 쓴 것」처럼 넣을 수 있다). 그래서 승인 화면과 §8.7의 「특정 사이트가 떠오르는지」 점검이 최종선이다.

**Phase.** L2·L3와 파일 op는 Phase 3, 사용자 블록은 Phase 3(블록 계약은 Phase 2), L4는 Phase 4 이후 사용자 결정.

**Phase 1 영향.** 필수 없음. 권장(선택): 겹 구조 로더, `theme.toml`의 `template_api = 1`.

**비용.** 파일 op·해시·역연산 3일, 오버레이 로더 1일(Phase 1에 겹 구조면 0.5일), 컨텍스트 계약 문서 2일, CSS 검사 2일, 자산 출처 검증 1일.

**대안.** 토큰만 허용(L0~L1): 안전하지만 「어떤 사이트든」의 디자인 다양성이 테마 수에 묶인다. 반대로 무제한 파일 편집을 changeset 밖에 두면 원칙 4(롤백)가 디자인에서 깨진다.

### 4.7 P7 — 사이트 프로필(단일 항목 데이터) (G7)

**제안.** `site_settings`에 구조화 키 `profile`을 둔다. 필드는 P1 타입 체계로 정의한다: 상호, 대표 문구, 주소, 좌표, 전화, 이메일, 영업시간(`list` of 요일·시간), SNS 링크, 사업자 정보 표시 여부. 영업시간·오시는 길·푸터·연락처 블록은 값을 따로 들지 않고 프로필을 참조한다. 검색 메타 출력도 같은 값을 쓴다(구체 형식은 구현 시 검색 엔진 공식 문서로 확인).

- Strapi의 single type(엔트리 하나만 관리하는 콘텐츠 타입)과 같은 역할이다. Maru는 범용 single type을 만들지 않고 「프로필」 하나로 시작한다. 필요가 반복되면 「단일 항목 컬렉션」으로 일반화한다.

**Phase.** Phase 2(블록이 참조) 또는 Phase 4(가게·기관 프리셋). 스키마 변경 없음(`site_settings` 키-값).

**Phase 1 영향.** 없음. **비용** 2일. **대안** 블록마다 값 보관(현재 SPEC 암묵안): 값이 어긋난다.

### 4.8 P8 — 폼 제출과 첨부 파일 (G5, G6)

**제안.** 둘 다 **공식 모듈**로 둔다(원칙 2). 코어는 필드 타입(P1)과 미디어만 제공한다.

- `forms` 모듈: 폼 정의(P1 필드 타입), `form_submissions` 테이블(모듈 마이그레이션, §7.1), 스팸 방지(rate limit, 숨김 필드), MCP `list_submissions`는 `"untrusted": true` + 본문 분리(§5.3, 원칙 6), 수집 동의 문구·보관 기간 설정과 자동 삭제. 알림은 관리 화면·MCP·이벤트(`form.submitted`)까지. 메일 발송은 SPEC에 SMTP가 없으므로 별도 결정. SMS는 범위 밖 유지.
  - 개인정보 수집(채용 지원, 행사 신청)의 법적 요건은 구현 시점에 공식 자료로 확인한다. 이 문서는 요건을 단정하지 않는다.
- `attachments`(또는 코어 미디어 확장): 문서 파일 허용 목록(PDF, HWP/HWPX, DOCX, XLSX 등, 확정은 보안 검토 후), 이미지가 아닌 파일은 재인코딩 대신 `Content-Disposition: attachment`와 `nosniff`로 내려보내고, 실행 파일·HTML·SVG는 거부. 글 첨부는 `media` 필드 타입(`many`)으로 연결. 자료실 = 첨부 필드가 있는 컬렉션 + 파일 목록 블록.

**Phase.** Phase 4(기관·채용·행사 프리셋과 함께).

**Phase 1 영향.** 없음(PHASE1_PLAN §1이 미디어 업로드를 Phase 1 제외로 이미 정함).

**비용.** `forms` 6~8일, 첨부 4~5일.

**대안.** 외부 폼 서비스 링크로 우회. 단일 바이너리·셀프호스팅 장점(원칙 5)과 어긋나고 데이터가 밖으로 나간다.

### 4.9 P9 — 기존 사이트 이전 (G10)

**제안: 무엇을 옮기고, 무엇을 옮기지 않는가**

| 구분 | 대상 | 판정 |
|---|---|---|
| 콘텐츠 | 사용자의 글·페이지·댓글·분류·태그 | **허용**. 사용자 소유 |
| 미디어 | 사용자가 올린 이미지·첨부 | **허용**. 단 원본 사이트에서 받아 오는 경우 소유 확인 필요(아래) |
| URL 구조 | 옛 주소 | **허용**. 리다이렉트(P4)로 보존 |
| 정보 구조 | 메뉴 트리, 페이지 계층 | **허용**. Maru 메뉴·페이지 트리로 재구성 |
| 브랜드 | 로고, 대표 색, 라이선스 확인된 폰트 | **허용**. 토큰과 미디어로 추출 |
| 디자인 코드 | 옛 사이트의 HTML 템플릿·CSS·JS | **이전 도구가 자동으로 옮기지 않는다**. Maru 블록·토큰으로 재구성 |
| 상용 테마 자산 | 구매한 테마의 코드·이미지 | **금지**. 테마 라이선스가 이식을 허용하는지 코어가 판단할 수 없다 |
| 제3자 사이트 | 남의 사이트 디자인·콘텐츠 | **금지**(원칙 7). 이전 도구의 대상이 아니다 |

- 디자인 코드 행이 사용자 결정 Q4다. 원칙 7의 문구(「특정 웹사이트의 코드·이미지·일러스트·화면 구성을 복제하지 않는다」)는 사이트 소유자를 구분하지 않는다. 이 제안은 「Maru가 제공하는 도구는 디자인을 재구성만 한다. 사용자가 직접 쓴 자기 테마 코드를 사용자 테마(L2)로 손수 옮기는 것은 막지 않는다」를 추천한다.

**소유 확인**

- 내보내기 파일을 사용자가 직접 주는 경로(WordPress WXR, 그누보드 DB 덤프, Markdown 폴더)는 그 자체로 소유 근거로 본다.
- 원본 사이트를 직접 읽는 경로(미디어 받아 오기, 내보내기 기능이 없는 사이트의 본문 추출)는 **소유 확인한 도메인에만** 허용한다. 예: 원본 사이트에 `/.well-known/maru-verify-<토큰>` 파일을 올리거나 DNS TXT 레코드. 확인 없이 임의 URL을 긁는 명령은 만들지 않는다. 에이전트가 제3자 사이트를 긁어 오는 통로가 되는 것을 막기 위해서다.
- 가져온 본문은 **데이터**다. ammonia 정화(§13), HTML→Markdown 변환, 그리고 프롬프트 주입 가능성 때문에 MCP 응답에서 `untrusted` 분리(§5.3)를 적용한다(원칙 6).

**소스별 경로**

| 소스 | 형태 | 우선순위 | 근거 |
|---|---|---|---|
| 그누보드 | DB 덤프 → 게시판·글·댓글·회원(비밀번호 해시 제외) | 높음 | 한국형 타깃, SPEC §2가 그누보드를 출발점으로 삼음 |
| WordPress | WXR 파일 | 높음 | 공식 문서상 내보내기 파일이 글·페이지·사용자 정의 글 유형·댓글·사용자 정의 필드·분류·태그·사용자를 담는 XML(WXR)이다. 미디어 파일 자체가 들어가는지는 해당 문서에 적혀 있지 않아, 미디어는 소유 확인한 원본 도메인에서 받는 경로로 설계한다 |
| Markdown 폴더 | 앞머리(front matter) + 본문 | 중간 | 정적 사이트 생성기 사용자 |
| Ghost 등 기타 | 각 공식 내보내기 형식 | 낮음 | 구현 시 공식 문서 확인 |

**흐름**: `maru import <source> --from <file> --dry-run --json` → 매핑 보고(컬렉션·필드·URL·건수·경고) → 구조는 changeset(컬렉션·페이지·메뉴·리다이렉트), 글은 ADR-0001에 따라 changeset 밖에서 `draft`로 일괄 생성(원래 발행일 보존) → `--publish`는 `publish` 스코프 필요. 재실행 멱등(원본 ID를 `meta.import_source`에 기록).

**Phase.** 코어 일괄 생성 API(발행일 보존, 원본 ID, 리다이렉트 생성)는 Phase 4. 소스별 가져오기는 공식 모듈(`import_gnuboard`, `import_wordpress`)로 Phase 4 이후.

**Phase 1 영향.** 없음.

**비용.** 코어 API 3일, 그누보드 5~7일, WXR 4~5일, 소유 확인 2일.

**대안.** 이전 도구 없이 에이전트가 글을 하나씩 `create_draft`로 옮김. 소규모는 되지만 URL 보존·발행일·댓글이 빠진다.

- `blog` 프리셋 TOML을 `[[ops]]` 목록 모양으로 쓴다(P5).

### 6.3 지금 하지 말아야 할 것

- `field_schema`, `meta`, `view_template`, `blocks`, `pages.parent_id` 등 컬럼을 Phase 1에 미리 추가하는 것. ADR-0010 위반이고, 이 제안의 정의(필드 타입 체계)가 확정되기 전에 컬럼부터 만들면 모양이 어긋날 수 있다.
- `boards` 테이블 이름 변경. 이득이 없다(P1 1항).
- 리다이렉트 테이블. Phase 1 슬러그 변경 이력은 `audit_log.diff`로 소급 가능하다(P4 4항).

## 7. 범위 밖과의 관계

SPEC §0의 범위 밖(쇼핑몰, SMS, 본인확인, 멀티 테넌트)은 **바꾸지 않는다.** 이번 목표 확대와 경계가 닿는 사례만 적는다.

| 사례 | 판단 | 이유 |
|---|---|---|
| 강의 수강료 결제 | 범위 밖 유지 | 쇼핑몰과 같은 결제·정산 문제. 외부 결제 페이지 링크로 우회 |
| 행사 유료 티켓 | 범위 밖 유지 | 같은 이유. 무료 신청은 `forms`(P8)로 범위 안 |
| 가게 예약 | 범위 밖 유지(현 시점) | 재고·시간 슬롯·노쇼 관리가 필요한 거래 시스템. 「예약 문의」 폼(P8)까지만 범위 안 |
| 채용 지원 시 본인확인 | 범위 밖 유지 | §0 본인확인 |
| 신청 알림 문자 | 범위 밖 유지 | §0 SMS. 관리 화면·MCP 알림까지 |
| 여러 사이트 한 인스턴스 | 범위 밖 유지 | §16 「사이트당 1 인스턴스」. 에이전시는 사이트마다 데이터 디렉터리 |

범위를 바꾸자는 제안은 없다.

## 부록 A. ADR 초안 (`docs/DECISIONS.md` 추가용)

> 형식은 기존 ADR과 같다(배경 · 결정 · 대안 · 결과). 채택된 것만 옮긴다.

### ADR-0016 늘어날 열거 값은 core에서 검증하고 DB CHECK를 걸지 않는다

- **배경:** 목표가 「콘텐츠 중심 사이트라면 무엇이든」으로 넓어지면서 `boards.kind`, `pages.layout`, `menus.location`, `audit_log.target_type`·`action`의 값이 Phase마다 늘어난다. SQLite는 ALTER TABLE로 CHECK 제약을 바꿀 수 없고, 바꾸려면 공식 문서의 12단계 테이블 재작성 절차가 필요하다.
- **결정:** 위 열거 값은 `TEXT NOT NULL`로만 두고 값 검증은 core 타입에서 한다. 상태 기계 값(`posts.status`, `posts.kind`, `actor_type`)은 값이 바뀌면 전이 규칙도 함께 바뀌므로 CHECK를 유지한다.
- **대안:** 모든 열거 값에 CHECK. DB 수준 무결성은 강하지만 값을 추가할 때마다 테이블 재작성 마이그레이션이 필요하다. 쓰기는 `WriteTx`(ADR-0007)를 통해 core만 하므로 core 검증으로 충분하다.
- **결과:** U3·U9 마이그레이션에 반영한다. DB를 직접 고치는 경우의 잘못된 값은 읽을 때 `INTERNAL`이 아니라 「알 수 없는 kind」 경고로 처리한다.

### ADR-0017 공개 URL은 단일 URL 빌더로만 만든다

- **배경:** ADR-0011이 공개 URL을 정했지만, 이후 컬렉션 퍼머링크·홈 교체·페이지 계층(ADR-0021)으로 URL 모양이 바뀐다. Phase 1부터 사용자 테마 복사가 가능하다(U10).
- **결정:** `url_for(Target)` 하나가 모든 공개 경로를 만든다. 템플릿은 `post.url`, `url_for()`만 쓰고 경로 문자열을 조합하지 않는다. 사이트맵, RSS, canonical, `next` 힌트, 관리 화면, CLI 출력이 같은 함수를 쓴다. 절대 URL은 `site_url` + 이 경로(ADR-0011 유지).
- **대안:** 템플릿에서 문자열 조합. 퍼머링크 변경 시 내장·사용자 테마를 모두 고쳐야 한다.
- **결과:** 내장 테마 검사 스크립트(PHASE1_PLAN §7)에 「템플릿 안 `/b/`, `/p/` 문자열 리터럴 금지」를 추가한다.

### ADR-0018 공통 필드 타입 체계

- **배경:** SPEC §2·§4의 `field_schema`는 「JSON Schema」로만 정의돼 렌더·검증·조회 계약이 없다. 블록(§8.5), 위젯(§7.2 `config_schema`), 모듈 설정(§7.1 `settings_schema`), 폼도 같은 문제를 가진다.
- **결정:** Maru 필드 타입(`text`, `textarea`, `markdown`, `number`, `boolean`, `date`, `datetime`, `select`, `multiselect`, `url`, `email`, `phone`, `media`, `ref`, `group`, `list`)을 정의하고 컬렉션·블록·위젯·폼·모듈 설정이 공유한다. JSON Schema는 필드 정의에서 생성해 MCP·REST 입력 스키마로 쓴다. 검증은 core에서 한다. `markdown` 타입만 정화된 HTML로 렌더한다.
- **대안:** 임의 JSON Schema 허용(렌더 계약 불가), 용도별 별도 스키마(중복).
- **결과:** Phase 2 산출물. 모듈 매니페스트(§7.1)의 `settings_schema`도 이 형식으로 바꾼다.

### ADR-0019 게시판을 정의 가능한 컬렉션으로 일반화한다

- **배경:** `boards.kind` 6개로는 포트폴리오, 행사, 채용, 강의, 매거진을 표현할 수 없다(제안서 §2).
- **결정:** `boards`·`posts` 단일 테이블 구조를 유지한 채, 컬렉션 정의(필드, 기능 플래그, 정렬 기준, 뷰, 퍼머링크)를 changeset op `collection.define`으로 만든다. `kind`는 닫힌 타입이 아니라 출발점 묶음이며 `custom`을 추가한다. meta 필드 필터·정렬은 `index: true` 필드만, SQLite JSON 식 부분 인덱스로 지원한다. 런타임 DDL은 필드 키 정규식 검증 후 `AssertSqlSafe`로만 실행한다. 뷰 템플릿은 `collections/{slug}` → `kinds/{kind}` → 기본 순서로 찾는다.
- **대안:** kind 추가(유형마다 코어 수정), 컬렉션별 테이블(그누보드식 회귀, SPEC §2에서 버림).
- **결과:** Phase 2(b). `field_schema`, `meta`, `view_template` 컬럼은 이때 추가한다(ADR-0010).

### ADR-0020 블록 타입과 위젯 타입을 하나의 렌더 계약으로 통합한다

- **배경:** SPEC은 위젯(§7.2)과 섹션 블록(§8.5)을 따로 두지만 둘 다 「스키마 + 렌더」다. 블록 데이터 모델과 렌더 계약이 없고, §8.5 카탈로그와 §8.6 프리셋 설명이 어긋난다(연혁, 조직도, 가격표).
- **결정:** `BlockType` 트레이트 하나(`id`, `name`, 필드 정의, `render`). 블록 인스턴스는 페이지 `blocks` 배열에, 위젯 인스턴스는 `widget_instances`에 저장하고 같은 타입을 가리킨다. 인스턴스는 `{id, type, v, variant, spacing, tone, data}`. 템플릿은 검증된 data와 선언형 질의 결과만 받는다. 블록 정의는 `block.toml` + `block.html`, 버전 변경은 선언형 변환만. 렌더 실패는 해당 블록만 비운다.
- **대안:** 위젯·블록 별도 유지. 모듈이 같은 기능을 두 번 등록하고 에이전트가 둘을 구분해야 한다.
- **결과:** Phase 2(a). 모듈 트레이트의 `widgets()`는 `block_types()`로 바꾼다. §8.5 카탈로그를 보강한다.

### ADR-0021 홈 설정, 컬렉션 퍼머링크, 페이지 계층, 리다이렉트

- **배경:** ADR-0003은 홈을 템플릿에 고정했고 ADR-0011은 URL 모양과 「슬러그 변경 시 404」를 정했다. 회사 소개·랜딩·문서·이전에서 막힌다.
- **결정:** `site_settings.home`(latest | page | collection), 컬렉션 `permalink` 패턴(`{slug}`, `{yyyy}`, `{mm}`, `{dd}`, `{category}`), `pages.parent_id`·`sort_order`와 경로형 URL, `redirects` 테이블(슬러그 변경 시 자동 301, Phase 1 이력은 `audit_log.diff`에서 소급), 예약 경로 목록과 충돌 시 `CONFLICT`. 라우트 표는 프로세스 캐시 없이 읽는다(PHASE1_PLAN §4.4). 기본값은 ADR-0011 그대로.
- **대안:** Ghost식 사용자 정의 라우트 파일. 표현력은 크지만 위 네 가지로 대부분의 수요가 풀린다. Phase 3 이후 필요 시 추가한다.
- **결과:** Phase 2(b). 라우트 변경은 구조 변경이므로 Phase 3부터 changeset 미리보기를 탄다. 다국어 접두어는 설계하지 않되 막지 않는다.

### ADR-0022 테마 자유도 단계와 테마 파일 changeset

- **배경:** 토큰(§8.2)과 사용자 테마 복사(§3.3, U10) 사이의 경계가 없고, 테마 파일 변경이 changeset(§6) 밖이라 원칙 4의 롤백이 디자인에서 깨진다.
- **결정:** L0 토큰, L1 블록 선택지, L2 템플릿 덮어쓰기·사용자 블록, L3 사용자 CSS 하나, L4 사용자 JS(사람 명시 허용 시만). L0~L3 변경은 changeset op(`theme.write_file`·`delete_file`, `base_hash`, 이전 내용 저장)로만. 템플릿 로더는 `changeset 오버레이 → 사용자 테마 → 내장` 겹 구조. `theme.toml`에 `template_api` 번호와 `[[assets]]` 출처·라이선스 목록, 목록 밖 자산은 검증 실패. 관리 화면은 덮어쓸 수 없다. 사용자 CSS는 외부 `@import`·`url()` 거부.
- **대안:** 토큰만 허용(디자인 다양성 부족), 파일 편집을 changeset 밖에 둠(롤백 불가).
- **결과:** Phase 3. 원칙 7은 자산 출처 목록, 승인 화면의 출처 표시, `AGENTS.md`의 「OO 사이트처럼」 처리 규칙으로 운영한다. 기술적으로 완전한 차단은 아니라는 점을 문서에 적는다.

### ADR-0023 프리셋을 조합 가능한 레시피로 재정의한다

- **배경:** 프리셋(§8.6)은 유형별 고정 세트라 조합(「카페 + 블로그 + 문의」)을 표현하지 못한다.
- **결정:** 레시피 = 매개변수화된 changeset op 묶음(`ensure` 의미로 멱등). 레시피 적용은 changeset 하나를 만든다. 프리셋 = 레시피 목록 + 테마 + 토큰. CLI `maru recipe`, MCP `list_recipes`·`apply_recipe`. 제안서 §2의 유형 매트릭스를 레시피 조합으로 정의해 Phase 4 회귀 시험으로 쓴다.
- **대안:** 프리셋 추가(조합 폭발), 에이전트의 저수준 op 직접 조립(품질 편차).
- **결과:** 형식은 Phase 3, 기존 5개 프리셋 재정의와 Phase 4 완료 기준 변경은 Phase 4.

### ADR-0024 기존 사이트 이전의 범위와 소유 확인

- **배경:** 실사용자는 기존 사이트에서 옮겨 온다. 원칙 7은 디자인 복제를 금지하고, 원칙 6은 외부 입력을 데이터로만 다룬다.
- **결정:** 이전 대상은 사용자 소유의 콘텐츠·미디어·URL·정보 구조·브랜드 토큰이다. 이전 도구는 디자인 코드(HTML·CSS·JS)를 자동으로 옮기지 않고 Maru 블록·토큰으로 재구성한다. 상용 테마 자산과 제3자 사이트는 대상이 아니다. 내보내기 파일(WXR, 그누보드 덤프, Markdown)은 사용자가 제공하고, 원본 사이트를 직접 읽는 기능은 소유 확인(`.well-known` 파일 또는 DNS TXT)한 도메인에만 허용한다. 가져온 본문은 정화하고 MCP에서 `untrusted`로 분리한다. 구조는 changeset, 글은 `draft` 일괄 생성(원 발행일 보존), 옛 URL은 리다이렉트.
- **대안:** 임의 URL 크롤링 가져오기. 에이전트가 제3자 사이트를 복제하는 통로가 된다.
- **결과:** 코어 일괄 생성 API는 Phase 4, 소스별 가져오기는 공식 모듈(`import_gnuboard`, `import_wordpress`)로 Phase 4 이후. 사용자가 직접 쓴 자기 테마 코드를 손수 옮기는 것의 허용 여부는 사용자 결정(제안서 Q4)에 따라 이 ADR에 적는다.

### ADR-0025 폼 제출과 첨부 파일은 공식 모듈로 둔다

- **배경:** 연락처 폼 블록(§8.5)과 「문의」(§5.3)는 있지만 제출 저장소가 없고, 자료실(§8.6 `org`)은 첨부 파일이 필요하다.
- **결정:** `forms` 공식 모듈(폼 정의는 ADR-0018 필드 타입, `form_submissions`, 스팸 방지, 수집 동의·보관 기간·자동 삭제, MCP 응답 `untrusted` 분리, `form.submitted` 이벤트). 첨부는 문서 파일 허용 목록, `Content-Disposition: attachment`·`nosniff`, 실행 파일·HTML·SVG 거부, `media` 필드 타입으로 연결. SMS 알림은 범위 밖 유지, 메일 발송은 별도 결정.
- **대안:** 외부 폼 서비스. 셀프호스팅·단일 바이너리 원칙과 어긋나고 데이터가 밖으로 나간다.
- **결과:** Phase 4. 개인정보 관련 법적 요건은 구현 시점에 공식 자료로 확인한다.
