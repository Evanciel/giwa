# 결제·예약·쇼핑 모듈 계획

## 배경

- ADR-0028 은 결제·쇼핑몰을 「Phase 5 이후 공식 모듈」로 미뤄 두었다(SPEC §0 의 「당분간 범위 밖」을 2026-11-02 결정으로 바꿈). 윅스 이상 작업(W1~W8)을 먼저 하느라 착수하지 못했다.
- 가게·병원·학원·숙소 사이트에서 결제와 예약이 없는 것이 지금 가장 큰 차이다. 사용자 지시(2026-11-12): 결제 모듈을 쉽게 붙일 수 있게 한다.
- 코어 도메인 6개에 결제는 없다(절대 원칙 2). 그래서 전부 모듈로 만들고, 모듈끼리는 정해진 확장 지점과 감사 기록 이벤트(ADR-0066)로만 이어진다.

## 공식 문서에서 확인한 것 (2026-11-12)

토스페이먼츠 (docs.tosspayments.com)
- 흐름: 서버가 `orderId`·금액을 먼저 저장 → 브라우저 SDK `requestPayment()` → `successUrl` 로 `paymentKey`·`orderId`·`amount`·`paymentType` 이 붙어 돌아옴 → 서버가 저장한 금액과 대조 → 승인 API.
- 승인 `POST /v1/payments/confirm` 본문 `paymentKey`(≤200)·`orderId`·`amount`. **결제 요청 뒤 10분 안에** 승인해야 한다(지나면 `NOT_FOUND_PAYMENT_SESSION`).
- `orderId`: 6~64자, 영문 대소문자·숫자·`-`·`_`·`=`.
- 인증: `Authorization: Basic base64("{시크릿키}:")`. 키 접두사 `test_`/`live_`. 주문서형·결제창형은 `gck`(브라우저)·`gsk`(서버) 한 쌍. 테스트 승인은 흉내일 뿐 돈이 빠지지 않는다.
- 취소 `POST /v1/payments/{paymentKey}/cancel` 본문 `cancelReason`(필수, ≤200)·`cancelAmount`(없으면 전액). 가상계좌는 `refundReceiveAccount` 필요.
- 조회 `GET /v1/payments/{paymentKey}`. (`orders/{orderId}` 조회는 `gsk` 로 못 부른다.)
- 멱등: 헤더 `Idempotency-Key`(≤300자, 15일 유효). 같은 키·URL·메서드면 첫 응답을 그대로 준다. 처리 중이면 409 `IDEMPOTENT_REQUEST_PROCESSING`.
- 상태: `READY`·`IN_PROGRESS`·`WAITING_FOR_DEPOSIT`·`DONE`·`CANCELED`·`PARTIAL_CANCELED`·`ABORTED`·`EXPIRED`.
- 웹훅: JSON POST, **10초 안에 200**, 실패하면 1·4·16·64·256·1024·4096분 뒤 7번까지 다시 보낸다. localhost 주소는 등록할 수 없다. `PAYMENT_STATUS_CHANGED` 에는 서명이 없고, `DEPOSIT_CALLBACK` 은 승인 응답의 `secret` 과 같은지 본다.
- 가입은 이메일만으로 되지만 주문서형·결제창형 키는 전자결제 신청 뒤에 보인다. 그 전에는 문서에 실린 공개 테스트 키를 쓰라고 안내한다.

포트원 V2 (developers.portone.io)
- 브라우저 `PortOne.requestPayment({storeId, channelKey, paymentId, orderName, totalAmount, currency})` → 서버가 `GET https://api.portone.io/payments/{paymentId}`(`Authorization: PortOne {API 시크릿}`)로 조회해 `amount.total` 대조, 상태 `PAID`·`VIRTUAL_ACCOUNT_ISSUED`.
- 웹훅 서명·테스트 채널은 5단계 착수 때 다시 확인한다.

전자상거래법 (공정위 결정문·시행규칙 인용 기준, 착수 때 law.go.kr 현행본 재확인)
- 제10조: 사이버몰 **초기 화면**에 상호·대표자 성명, 영업소 주소(불만 처리 주소 포함), 전화·전자우편, 사업자등록번호, 호스팅 제공자 상호. 이용약관은 연결 화면이어도 된다(시행규칙 제7조).
- 제13조: 통신판매업 신고번호와 신고 기관을 표시한다.
- 거래 기록 보존: 계약·청약철회·대금 결제 5년, 소비자 불만·분쟁 3년(제6조·시행령 제6조). 주문의 구매자 정보는 보존 기간이 지나면 익명화한다.

## 결정 (추천안대로)

| 항목 | 결정 |
|---|---|
| 모듈 나누기 | `mods/pay`(주문·결제·환불, PG 어댑터), `mods/booking`(예약), `mods/shop`(상품·장바구니·배송). 예약·쇼핑은 결제 없이도 켤 수 있다 |
| 모듈 사이 연결 | `maru-modules` 에 `Checkout` 확장 지점(주문 만들기·주문 보기)을 새로 둔다. 예약·쇼핑은 이것만 부르고 `pay` 크레이트를 모른다. 결제 완료·환불은 감사 기록 `pay.paid`·`pay.refunded`(target = 주문, 내용에 `owner`·`ref`)로 받는다. 배달은 최소 한 번이므로 받는 쪽이 멱등하게 |
| PG 어댑터 | `pay` 안의 `Provider` 트레이트: `prepare`(브라우저에 줄 값)·`confirm`·`lookup`·`cancel`·`parse_webhook`. 처음 둘: `bank`(무통장 입금. PG 계약 없이 바로 쓴다. 계좌를 안내하고 운영자가 입금을 확인), `toss`. 5단계에 `portone` |
| 금액 | 원(KRW) 정수만. 금액은 **늘 서버가 정한다**: 결제 단추 설정·상품 가격·예약 예약금에서 계산해 주문에 적는다. 브라우저가 보낸 금액은 대조에만 쓴다 |
| 주문 ID | 서버가 만든 무작위 24자(영숫자). 토스 `orderId` 규칙(6~64자) 안 |
| 주문 상태 | `pending` → `paid` / `failed` / `expired`, `paid` → `refunded` / `partial_refunded`. 무통장은 `awaiting_deposit` → `paid`. 바뀔 수 있는 길만 허용하는 함수 하나로 지킨다(같은 알림 두 번이면 아무 일도 없음) |
| 승인 | 돌아오는 주소에서 주문을 찾고, 금액·상태(`pending`)·10분 안을 확인한 뒤 승인 API. `Idempotency-Key` = 주문 ID. 응답의 상태·금액을 다시 대조하고 나서야 `paid` |
| 웹훅 | `POST /m/pay/webhook/<provider>`. 본문은 믿지 않는다: `paymentKey` 만 꺼내 **조회 API 로 다시 물어** 그 결과로 맞춘다. `DEPOSIT_CALLBACK` 은 저장해 둔 `secret` 과 같아야 한다. 늘 빨리 200 |
| 환불 | 사람(운영자, 새 권한 없이 코어 `Permission` 중 사이트 설정 권한)만. 전액·부분, 사유 필수. `Idempotency-Key` = 환불 ID. 에이전트 툴은 보기·환불 **제안**까지만, 실제 환불은 사람이 관리 화면에서 누른다(절대 원칙 4) |
| 비밀값 | 시크릿 키는 모듈 표에 두고 화면·JSON 에는 끝 4자만(소셜 로그인 `secret_hint` 방식). 감사 기록 diff 에도 남기지 않는다 |
| 운영 키 잠금 | `live_` 키는 사이트 사업자 정보(아래)가 다 채워져 있고 `site_url` 이 https 일 때만 저장된다. 에러에 빠진 칸과 다음 명령을 적는다 |
| 사업자 정보 | 코어 사이트 설정(표현 도메인)에 `business`(상호·대표자·주소·전화·전자우편·사업자등록번호·통신판매업 신고번호·신고 기관·호스팅 제공자). 채우면 모든 테마 바닥글에 나온다. 이용약관·환불 규정 페이지를 프리셋 페이지로 준다(내용은 운영자가 고친다는 안내와 함께) |
| 결제 화면 | `/m/pay/checkout/<주문>`: 주문 내용·금액·환불 규정 연결·동의 칸 → PG 창. 토스 SDK 스크립트(`js.tosspayments.com`)는 이 화면에만 CSP 로 허용한다. 영수증 `/m/pay/receipt/<주문>?k=<1회용 값>` |
| 결제 단추 | 모듈 위젯 `pay_button`(이름·금액 고정, 또는 「금액 직접」은 최소·최대를 운영자가 정함). 상담비·수강료·후원처럼 상품 목록이 필요 없는 결제 |
| 구매자 정보 | 이름·전자우편·전화(선택). 회원이면 채워 둔다. 결제 끝나면 확인 편지(기존 보낼 편지함) |
| 오래된 주문 | `pending` 은 1시간 뒤 `expired`(모듈 `purge`). 구매자 정보는 5년 뒤 익명화 |
| 신호 | 모듈 `signals`: 입금 대기 n건, 승인됐는데 맞추지 못한 주문, 웹훅 주소가 공개 주소가 아님 |
| 시험 | 게이트는 인터넷에 닿지 않는다: e2e 가 가짜 PG 서버(axum)를 띄우고 어댑터 기준 주소를 시험용 환경 변수로 바꾼다. 실제 토스 샌드박스 결제는 공개 테스트 키로 브라우저에서 한 번 하고, PG 결제 창이라 커밋 전 사용자 확인을 받는다 |

## 예약 모듈 (3단계)

| 항목 | 결정 |
|---|---|
| 대상 | 「서비스」(진료·상담·수업·객실 등) 여러 개. 각자 소요 시간·정원·가격·예약금 |
| 시간 | 요일별 영업 시간 + 쉬는 날 + 막은 시간. 한국 시간 기준, 칸은 서비스 소요 시간 단위 |
| 겹침 | 같은 칸의 확정·대기 예약 수가 정원을 넘지 않게 트랜잭션 안에서 센다. 예약금 결제 대기는 15분 동안 자리를 잡아 둔다 |
| 흐름 | 날짜 → 시간 → 이름·연락처 → (예약금 있으면) 결제 → 확정 편지. 예약금 없으면 바로 `requested`, 운영자가 확정 |
| 취소 | 손님은 편지의 1회용 링크로, 운영자가 정한 시간 전까지. 예약금 환불은 `pay` 의 환불(사람 승인)로 |
| 화면 | 위젯 `booking_form`, 관리 화면 날짜별 목록·확정·취소, 툴 `list`·`slots`·`set_hours` |

## 쇼핑 모듈 (4단계)

| 항목 | 결정 |
|---|---|
| 상품 | 이름·가격·사진(미디어 도메인)·설명·재고(없으면 무제한)·옵션 한 단계(크기·색) |
| 장바구니 | 손님은 쿠키에 담는다(서버 표에 30일), 회원은 회원에 묶는다. 담을 때와 결제 직전에 가격·재고를 서버가 다시 읽는다 |
| 재고 | 결제 완료(`pay.paid`) 때 줄인다. 모자라면 그 주문을 자동 환불 제안으로 올리고 운영자 신호 |
| 배송 | 고정 배송비 + 얼마 이상 무료. 주소 입력(우편번호 찾기는 외부 스크립트 없이 직접 입력부터), 운송장 번호 칸 |
| 주문 관리 | 상태 `paid` → `preparing` → `shipped` → `delivered`, 바뀔 때 손님에게 편지 |
| 화면 | 상품 목록·상품 화면·장바구니·주문 조회(회원 또는 주문번호+전자우편), 위젯 `product_grid` |

## 순서

1. **결제 뼈대**: `maru-modules` `Checkout` 확장 지점 → `mods/pay` 마이그레이션(`mod_pay_order`, `mod_pay_payment`, `mod_pay_refund`, `mod_pay_provider`, down) → 상태 전이 함수·`bank`·`toss` 어댑터 → 돌아오는 주소·웹훅·조회 → 툴(`orders`, `order`, `provider_set`, `refund_propose`) → 가짜 PG e2e(승인 성공·금액 위조 거절·10분 지남·웹훅 두 번·본문 위조 무시·환불 멱등)
2. **결제 단추와 법 표시**: 코어 사이트 설정 `business` + 바닥글 + 약관·환불 규정 프리셋 페이지 → `pay_button` 위젯·결제 화면·영수증·확인 편지 → 관리 화면(주문 표·환불·키 설정) → 운영 키 잠금 → 공개 테스트 키로 실제 샌드박스 결제(사용자 확인)
3. **예약 모듈**: 위 표대로. 예약금은 `Checkout` 으로. e2e: 정원 경쟁(동시 두 요청), 예약금 결제 뒤 확정, 15분 지난 자리 풀림, 1회용 취소 링크
4. **쇼핑 모듈**: 위 표대로. e2e: 가격을 바꾼 뒤 결제하면 새 가격, 재고 0 동시 결제, 배송 상태 편지
5. **포트원 어댑터**: 공식 문서(웹훅 서명·테스트 채널) 재확인 뒤 `portone`. 이니시스·KCP·카카오페이·네이버페이를 포트원 콘솔 채널로 연결

각 단계 끝에 ADR 을 쓰고, 게이트·브라우저 확인 뒤 커밋·미니PC 배포. 1단계만 해도 무통장 입금으로 실제 주문을 받을 수 있고, 2단계가 끝나면 토스 테스트 결제가 화면에서 끝까지 된다.

## 사용자 몫 (막지 않고 남은 일로 적는다)

- 토스페이먼츠(또는 포트원) 가입·전자결제 신청·가맹 심사, 운영 키(`live_`) 입력.
- 사업자 정보·통신판매업 신고번호 입력, 이용약관·환불 규정 내용 확정.
- 공개 사이트에서 웹훅을 받으려면 PG 관리자 화면에 `https://<사이트>/m/pay/webhook/toss` 를 등록.

## 하지 않는 것

- 카드 정보 저장·자동 결제(빌링키), 정기 구독, 해외 결제, 현금영수증 발행 API, 에스크로, 오픈마켓(여러 판매자). 필요해지면 따로 계획한다.
